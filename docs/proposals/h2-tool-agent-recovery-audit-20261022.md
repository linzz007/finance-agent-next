# H2 主 Agent 与工具调用链路核查

日期：2026-10-22。
状态：当前仓库实现的核查说明及下一步讨论建议，不是已确认的新设计。

本轮没有修改运行代码、重启服务、调用付费模型或追加预算。本文检查仓库最新
H2 实现，不以历史网页进程证明最新规则资产已经加载。101 的进程更新限制仍见
[规则资产验证记录](../acceptance/h2-external-rules-20261022.md)。

## 1. 先给结论

H2 已经实现真正的持久化 Agent 执行链路，不能再称为只使用旧同步委派。
但它是借鉴 Codex 等系统后为金融研究实现的自有 Harness，**不是完整复刻 Codex**。
特别是工具失败的分类与恢复仍不统一，不能称为所有工具故障都能稳定恢复。

| 用户关心的情况 | 当前行为 | 仍需区分的边界 |
| --- | --- | --- |
| 模型输出半截 JSON | 拒绝执行；有限文本规范化；一次定向模型补正 | 补正仍不合法可终止当前 Task，不保证 Root 有终稿 |
| JSON 合法，工具参数错误 | 输入 Schema/权限检查；多数可反馈错误成为失败观察 | 不会自动推断正确业务意图；也不是每种错误都能纠正 |
| 工具暂时不可用 | 部分来源有底层重试；适配器返回失败或异常传播 | 尚无统一错误分类、退避、幂等与执行结果未知处理策略 |
| 工具结果进入上下文 | 保存 Artifact、观察与检查点，下次调用重新装配 | 已进入输入不等于模型真正理解；超限时可能只提供展开引用 |

稳定性的目标应是：可识别的可恢复错误允许继续；不可恢复错误明确报告；
不重复危险副作用、不虚构工具成功、不吞掉已有分析，而不是保证任意错误都会成功。

## 2. 当前真实执行顺序

```text
从 SQLite/Artifact 恢复任务状态和观察
  -> 加载本 Run 冻结的规则资产、工具目录和角色规则
  -> 组织下一次模型输入
  -> 获取完整公开响应，检查正常结束状态
  -> 规范化、解析、校验 AgentAction
  -> 保存 prepared_action 和检查点
  -> 检查工具授权、校验工具参数、执行工具
  -> 保存原始工具结果 Artifact 和动作观察
  -> 更新真实读取/来源状态
  -> Worker 持久化继续状态并重新入队，安全结算后 ACK
  -> 下一 Attempt 重新装配输入，模型选择下一步
```

主要入口：`src/policy_impact/dispatch/finance_agent.py` 的 `__call__`、
`_business_action`、`_finish_business_action`、`_messages`；持久化边界在
`worker.py`、`repository.py` 和 `execution.py`。

本项目选择每次决策一个动作、每步落盘后继续。单 Agent 的这一动作序列是串行的；
多个子 Agent 可由不同 Worker 并发运行，两者不是同一种并行。

模型实际走公开文本动作协议，不是供应商原生 `function_call`。即使传输使用
Responses，也不自动变成原生工具调用。现有设计不因本报告擅自切换协议。

## 3. 半截 JSON：不要把流式片段当作可执行动作

### 3.1 两种不完整要分别看

- 流式响应还没结束：继续等待完整响应，不能拿已到达的片段执行。
- 响应已经结束，但内容缺括号、缺字段或被输出长度截断：协议失败，不能猜着执行。

例如模型只返回：

```text
{"type":"tool_call","tool_name":"article.read","arguments":{"article_id":"a1"
```

当前代码不会补出结尾后擅自调用 `article.read`。因为无法证明丢失的只是括号，
还是还存在未输出的参数、条件甚至不同动作。

### 3.2 已有的确定性处理

`finance_actions.py` 提供受限规范化：单层且仅包含一个对象的代码围栏、
字符串中的裸控制字符及非法反斜杠转义、有限的外层标签兼容。
非围栏文本只选首个完整对象，其尾部保留审计但不执行；首对象非法时不能跳到
第二个对象。已有 DSML 兼容是独立、有界的供应方适配，不是任意 XML 都可信。

这些规则不创造缺失字段、参数、证据 ID 或工具执行结果。规范化后仍须通过完整校验。

### 3.3 一次补正到底改变了什么

`FinanceH2Domain._decide` 的补正输入是：

```text
原始可信 system/user 输入
+ action-repair 指令
+ 完整动作 JSON Schema
+ 字段错误路径，或语法错误的行/列/偏移
+ 最多 160 字符的语法形状片段，内容值被遮蔽
+ 子任务终稿需要时的结果 Schema
```

完整被拒输出只保存在审计中，不整段回灌，避免它夹带自造工具结果或指令。
规则要求同模型、原预算，仅修正公开结构；只能从真实任务与观察重建，不能新增
虚构来源。部分证据锚点问题另走冻结正文后的补丁协议，补丁失败可保留完整分析并警告。

所以它不是原封不动再次抽样。第二次成功率应实测条件概率，不能假设仍为 70%，
也不能用独立事件的公式推算总成功率；同一模型的系统性错误通常相关。

但当前补正也有实质限制：一般动作输出补正仍失败，会传播终态错误，Worker 可把
当前 Task 标记失败。若是子任务，父任务可看到失败后另作安排；若是 Root，可能没有
用户可用终稿。现有候选和审计被保留，不等于已经交付自然语言答案。

补正请求仅在传输错误时允许原请求重发一次。此分支最多是原调用、补正、补正重发
三次物理请求，不是整轮任务最多三次。普通模型传输失败另有 Attempt 恢复边界；
它们不能与格式补正混为一个无限重试机制。

## 4. JSON 合法但参数错误：形成真实失败观察

例如模型发出：

```json
{"type":"tool_call","tool_name":"article.read","arguments":{"id":"article_alpha"}}
```

外层动作可以合法，但工具实际要求 `article_id` 而不是 `id`。
工具参数模型使用严格类型并禁止额外字段；工具说明与参数检查共用模型来源。
这次不会读取文章，产生的工具负载大致为：

```json
{
  "tool":"article.read",
  "ok":false,
  "error":{
    "code":"invalid_arguments",
    "message":"No successful source read. Inspect the exact tool contract and granted materials.",
    "describe_name":"article.read",
    "issues":[
      {"path":["article_id"],"type":"missing"},
      {"path":["id"],"type":"extra_forbidden"}
    ]
  }
}
```

Runtime 再把它包成带 `action_key`、`tool_name`、`status=failed` 的动作观察，
保存 Artifact，把引用记入研究状态。下一次 `_messages` 把它加载到
`action_observations`，模型由此知道“读失败了”，而不是把它当文章正文。

一种正常纠正路径是：

```text
错误的 article.read
 -> 下一决策看到 failed + 缺失字段路径
 -> tool.describe(name="article.read")
 -> 下一决策看到实际参数 Schema
 -> article.read(article_id="article_alpha", start_line=1, limit=100)
 -> 实际成功读取后才更新来源和证据状态
```

本轮定向测试验证了包含发现和终稿的五步持久化链路，实际文章读取只有一次。
不过这是脚本模型的可执行路径，不保证真实模型每次一定选择查询说明。

还要区分三种“参数有问题”：

- 类型/名称/范围错误：程序通常能检测。
- 不存在或未授权的材料：领域和权限层拒绝；不能靠重试创造授权。
- 参数合法但选错作者、日期或研究范围：可能正常执行，属于研究决策错误，
  Schema 不会自动理解用户意图并修正它。

调度类工具也有失败观察，但当前部分反馈仅有通用消息，未提供业务工具同样细的
字段诊断。这是反馈一致性不足，不宜宣称所有工具都已有同等恢复质量。

## 5. 工具不可用：目前有局部兜底，没有统一恢复策略

### 5.1 网页工具的实际行为

- `web.open` 使用 `fetch_url`，调用设置 `retries=1`：通常是一次获取加一次重试。
- 获取超时参数为 18 秒；默认重试延迟起点为 0.25 秒。这是单次获取设置，
  不是整个工具调用永远只耗时 18 秒。
- `web.search` 依次尝试 `bing`、`auto` 搜索后端；这是来源策略，不是切换付费模型。
- 仍无法获取时，适配器可返回 `ok=false/status=unavailable`，例如
  `public_source_unavailable`。Runtime 保存失败观察，Agent 决定改来源、继续其他工作
  或在答案中披露未核实。
- 搜索线索、空内容、获取失败不能晋升为已读网页证据。

### 5.2 现有不足

网页适配器把若干异常统一折叠为 `public_source_unavailable`；网络超时、HTTP 拒绝、
提取失败乃至部分安全拒绝，可能得到近似反馈。这样能防异常文本泄密，但不足以让
Agent 或 Runtime 精确区分“可稍后重试”“必须改参数”“没有权限”“内容类型不支持”。

底层 HTTP 重试当前是广泛捕获异常后重试，不是按状态码精细区分的统一退避机制；
本次没有发现统一的 `Retry-After`、指数退避加抖动或跨工具熔断策略。行情等适配器有
自己的错误处理，也不能把网页的重试次数套给所有工具。

未被转换的异常仍可能传播。尤其数据库/Artifact 存储故障不能伪装成可忽略的工具失败；
Worker 对这类故障保留安全结算边界，不应在持久化失败后提前 ACK。

### 5.3 不能把持久化误称为外部恰好执行一次

`prepared_action` 让恢复后的执行器知道已经决定了什么，调度命令另有幂等保护；
这不保证所有外部工具在“已经执行但结果尚未落盘时崩溃”的窗口都只执行一次。
当前确定性读取缓存也只覆盖指定工具，不是所有工具的通用执行账本。

只读研究工具重复获取通常不产生业务写入，但可能消耗时间、费用或返回不同数据。
未来若增加下单、发信或修改外部数据等工具，必须先定义幂等键、执行结果未知和
人工确认策略，不能直接沿用只读获取的重试逻辑。本报告不授权增加这些工具。

## 6. 工具结果怎样进入上下文

工具并不直接修改模型的“记忆”。Runtime 保存结果后，为下一次请求重新构建输入。

1. 工具返回原始业务负载，完整内容存为不可变 Artifact。
2. 保存动作观察，关联动作键、工具名、成功/失败和负载。
3. 成功且满足来源条件时才更新文章读取状态、来源与证据账本。
4. Worker 保存继续状态和检查点，安排下一 Attempt。
5. 下一次模型输入包含 `query`、计划、材料、文章状态、证据账本、动作观察、
   子任务状态、预算和工具目录，而不是仅给一句“上次失败了”。

重复负载在输入呈现中去重，原始存储保留。超过输入边界时，部分正文被换为引用和
`material.get`/`context.open` 展开入口；不保证所有完整正文永远同时在上下文中。

完整保存、当轮注入、模型实际利用是三个不同命题。当前没有“因为内容已存储，
所以模型必然全部理解”的保证，也没有完善的语义相关性选择器。

金融网页等已有来源身份、范围、哈希或快照校验，但不是所有工具共享一份同样强的
输出契约。完整结果进入上下文前的验证和不可信数据边界，仍值得统一设计。

## 7. 与 Codex、Pi、DeepSeek Harness 对照

### 7.1 本轮实际可查证的官方文档

- [OpenAI Function calling](https://developers.openai.com/api/docs/guides/function-calling)：
  模型发出调用，应用执行，再以匹配 `call_id` 的结果继续模型请求；支持严格 Schema。
  严格 Schema 约束格式，不等于事实正确或业务意图正确，也不代替超时与权限处理。
- [Codex App Server](https://learn.chatgpt.com/docs/app-server)：公开 Thread/Turn/Item、
  工具开始与完成事件、`mcpToolCall` 的结果/错误、动态工具的结果与成功状态，
  以及工具输出保存在历史并进入后续模型输入的机制。
- 同一 App Server 文档针对请求入口过载明确建议指数退避和抖动；这是入口过载策略，
  **不能外推为 Codex 对每个工具、每种错误都采用相同重试规则**。

这些资料证明分层和生命周期；没有证明“Codex 对任何坏 JSON 必定重试 N 次”或
“Codex 永远能从任意工具错误中恢复”。本轮未新读 Codex 工具路由器源码，不冒充
已逐项核实其最新内部实现。既有 Codex 源码研究固定在 2026-10-17 的提交，主要涉及
多 Agent 身份/调度/邮箱/历史，见[历史调研](harness-v2-multi-agent.md)。

### 7.2 本轮重新读取的本地框架快照

[087](../changes/087-h2-framework-informed-json-escape-repair.md)登记了固定来源提交。
本轮重读的是 `runtime-records/framework-research-20261020` 下的既有副本，
不是声明获取了框架最新版本，也没有把它们作为项目依赖引入。

- Pi 的 `json-parse.ts` 明确分开流式部分解析与终态参数解析；终态坏参数保留
  `argumentsError`，不能因为流式预览能拼出部分对象就执行。
- Pi 的 `agent-loop.ts` 在执行前校验参数，未知工具、参数错误、阻止执行与普通执行
  异常转成 `isError=true` 的工具结果，由后续模型决策继续处理。
- DeepSeek Harness 的 `tool-calls.ts` 保留无法 JSON 解析的原参数，Schema 层检查，
  工具结果按调用身份写入会话并安排下一步上下文；还能区分并发与独占工具，
  执行可重叠而结果按模型调用顺序提交。

核心可借鉴点不是“宽松猜出一个 JSON”，而是把错误局部化成有身份的工具结果，
保持调用与返回配对，避免普通工具错误直接摧毁整个任务。
本项目的公开文本动作若连外层身份都无法解析，就不能照搬“已有可信 call_id 的坏参数”
处理方式；应先区分可信调用外壳与不可信参数，而不是凭空创建成功调用。

### 7.3 已有与未有

| 能力 | 本项目现状 |
| --- | --- |
| 模型选择动作，执行层校验和执行 | 已实现 |
| 工具说明、角色规则外置且按 Run 固定 | 101 已实现，运行进程加载须单独确认 |
| 持久化 Thread/Task/Attempt、检查点、Outbox、租约 | H2 已实现，不是 Codex 内部结构的同名复制 |
| 动作/结果关联、失败观察进入下一次模型输入 | 已实现，但反馈细度不完全一致 |
| 统一可插拔工具执行流水线 | 参数注册已共享；业务路由仍有集中分支，未完全统一 |
| 同一决策批量并行调用工具与独占屏障 | 当前公开动作一次一个，不等同于多子 Agent 并发 |
| 跨工具统一失败分类、可恢复性、退避与结果未知契约 | 未完整实现 |
| 所有格式失败都不会导致 Root 无终稿 | 未保证 |
| Codex 整套客户端、协议、安全、工具能力完全复刻 | 未实现，也不宜把金融所需边界外的功能作为目标 |

Claude Code 的内部 Harness 不能仅凭公开使用文档认定全部可知。本报告不虚构
其私有源码、重试次数或数据库结构；比较重点是可证实的机制，而不是产品名。

## 8. 建议下一步只设计这一段，不扩大成全系统重构

以下均为待确认建议：

1. 定义一份统一工具结果和错误契约：错误阶段、错误类别、是否允许恢复、
   安全诊断、结果引用、分页/截断、调用关联和实际执行状态。
2. 把普通工具失败与 Runtime 致命失败分开。可识别调用的参数错误交给 Agent
   纠正；全坏动作走有界补正；存储失败、授权失效等仍保留强边界。
3. Runtime 只对确定可安全重试的暂时故障执行有界重试；错误参数由模型重规划，
   权限错误不靠重试解决，外部副作用结果未知不盲重放。
4. 对重复且没有进展的失败定义停止条件，同时保存候选、允许披露缺口；不以新增
   金融审核门控阻止可用答案，也不承诺格式完全不可解析时必定有可信终稿。
5. 工具执行流程逐步统一为描述、校验、授权、执行、结果验证、保存、上下文投影。
   先覆盖现有只读金融工具，不先造大而全框架，不改模型或预算。

验收指标应包括首轮遵约率、按错误分类的恢复率、恢复新增调用/耗时、
不该重试时的零重试、调用/结果错误绑定数、重复副作用数、失败后可用交付率，
以及故障注入后的恢复正确性。不能只统计 JSON 最终能解析的比例。

**18 passed, 328 deselected in 16.74s**。零付费模型调用。

涉及 `test_dispatch_finance_rules.py`、`test_dispatch_execution.py`、
`test_dispatch_public_sources.py`、`test_dispatch_market_sources.py`、
`test_dispatch_finance_continuation.py`，覆盖：
