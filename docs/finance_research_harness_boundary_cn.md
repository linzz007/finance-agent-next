# 金融研究 Agent 的自治边界与证据闭环

## 1. 最终设计判断

本项目不应该把大模型改造成一个固定模板生成器。更合理的边界是：

- **模型负责**：理解问题、选择检索方式、决定是否继续读取、组织分析、决定是否需要质疑或核验、生成最终答案。
- **Runtime 负责**：工具是否存在、路径是否越界、来源是否真的读过、引用是否可追溯、子智能体是否有权限、运行是否超预算、失败是否留痕。
- **用户负责**：提供或修改文章、研究偏好和持仓等事实；确认需要长期记忆的内容。

核心原则：**不限制模型怎么思考，但限制模型能依据什么、能调用什么、能写入什么。**

## 2. 当前架构是否自己实现

当前核心 AgentRuntime、AgentLoop、TurnCoordinator、ToolGateway、PermissionEngine、Trace 和文章研究网关是项目自己的实现，不依赖 LangGraph 或 LangChain 作为核心执行框架。

当前使用外部库主要是工程基础设施：

- FastAPI / Uvicorn：HTTP API 和服务启动；
- Pydantic：动作、请求和内部结果的 Schema 校验；
- SQLite：文章索引、运行记录和可重建状态；
- 浏览器与标准 Python 能力：前端和文件处理。

这条路线应保留。可以借鉴 Claude Code、Codex、Pi Agent SDK 的 Loop、Tool、Context 和权限设计，但不建议把核心 Runtime 替换成第三方框架。否则项目最有区分度的“执行语义由自己掌握”会消失。

## 3. 工具分层

### 3.1 研究 Agent 可以使用的工具

当前金融文章研究网关提供：

| 工具 | 作用 | 约束 |
|---|---|---|
| `article.search` | 搜索本地博主文章 | 返回候选，不等于证据 |
| `article.read` | 读取文章指定行 | 只能读取索引文章的有限行数 |
| `article.claims` | 抽取文章中的原文主张 | 结果是作者主张，不是事实 |
| `source.discover` | 找公开来源线索 | 标题和聚合页只能作为线索 |
| `source.fetch` | 读取允许域名的一手页面 | 必须匹配具体原文段落才能核验 |

这些工具足以支持“文章获取、原文提炼、外部查证、交叉分析”。模型可以自主决定调用顺序，不需要把流程写死成固定 DAG。

### 3.2 不建议直接暴露给模型的工具

不建议把任意路径的 `read_file`、`write_file` 直接暴露给模型。

- 任意读文件会造成跨工作空间和隐藏文件泄露；
- 任意写文件会污染原始文章、Wiki 或持仓数据；
- 工具名虽然简单，但无法表达研究语义和写入边界。

正确做法是使用领域工具：

- 用户添加文章：通过文章 API 或“添加文章”页面写入指定博主的 `articles` 目录；
- Agent 读取文章：使用 `article.search` / `article.read`；
- Agent 保存运行结果：使用受控 `artifact.write`，只能写当前 run 的产物目录；
- 未来需要修改 Wiki：单独设计 `wiki.patch`，必须要求用户确认并记录版本。

## 4. 推理准确性的两层验证

不能证明模型的每一步隐式思考绝对正确，也不应该要求模型输出完整 Chain of Thought。应该验证可审计的外部结果。

### 第一层：信息来源验证

1. 文章是否来自当前文章库；
2. 文章是否被本轮实际读取；
3. 引用的路径、行号和内容是否一致；
4. 作者观点是否和官方事实分开；
5. 外部来源是否为允许域名；
6. 抓到标题是否被错误地当成原文证据。

这一层当前已有 `article.search`、`article.read`、`source.fetch` 和引用门控，后续要继续强化检索质量。

### 第二层：分析链验证

模型可以自由选择分析方法，但每个可审计结论应留下最小结构：

```text
Claim：本轮得出的判断
Type：事实 / 作者观点 / 推断 / 预测
EvidenceRefs：支撑它的文章行号或官方来源
Assumptions：依赖的前提
Status：supported / mixed / unsupported
```

这只是 Trace 中的内部证据账本，不是强制用户看到的最终格式。最终回答仍然可以由模型根据问题自由组织。

复杂问题再调用 `skeptic` 或 `verifier`：它们只读取主 Agent 已经提供的证据，检查反例、跳步、证据不足和来源混淆；主 Agent 再决定是否修改结论。

## 5. Prompt 的最终原则

系统 Prompt 只需要说明：

1. 当前工作空间和文章库在哪里；
2. 当前有哪些工具、参数和权限；
3. 文章观点、官方事实、推断和预测必须分开；
4. 需要核验时如何调用来源工具；
5. 什么时候委派 Subagent；
6. 最终答案不能编造没有读取的来源。

不要在系统 Prompt 中写死长篇分析模板，也不要要求所有问题都输出相同章节。报告风格、对比风格、简答风格可以作为可选 Skill，由用户显式选择或由主 Agent 根据问题决定。

## 6. 下一轮实现顺序

1. 将文章检索从当前关键词评分升级为 SQLite FTS5/BM25，并保留作者、主题、日期过滤。
2. 加入文章 hash 去重和版本记录，避免重复上传同一篇文章。
3. 建立内部 Evidence Ledger，记录 Claim、证据引用、假设和验证状态。
4. 在主 AgentLoop 中按需委派 analyst / skeptic / verifier，展示每个子任务的上下文和结论。
5. 用真实问题验证：单篇总结、作者比较、官方核验、多轮追问、无证据拒答、新增文章后重查。

这五步完成后，系统才算从“能读文章并回答”提升到“能自主研究，但每个关键结论都可复盘”。

## 7. 分层检索设计

金融文章的“定位文章”和“理解文章”必须分开。不能把所有文章全文一次性放入上下文，也不能把搜索摘要直接当作证据。

### 7.1 Wiki 层：确定研究范围

Wiki 不负责存放全部文章正文，而是提供本轮研究的约束和偏好：

- 用户身份、关注主题和资产范围；
- 关注的作者或博主；
- 时间窗口和更新频率；
- 研究偏好，例如优先官方来源、区分事实和预测；
- 持仓或观察标的等用户明确提供的事实。

它回答的是：“这次应该关注什么”。

### 7.2 文章目录层：定位独立文章

文章库中的每篇文章是一个独立检索单位，至少包含：

```text
article_id / author / title / published_at / source_url
content_hash / version / topic_tags
```

这一层使用元数据过滤、FTS5/BM25、关键词和主题扩展，输出候选文章 ID，不直接输出最终结论。

它回答的是：“哪些文章可能相关”。

### 7.3 文章内容层：读取可引用原文

主 Agent 根据候选文章 ID 调用 `article.read`，按行读取相关范围。文章较短时可以读取全文，文章较长时先读取标题、目录和相关段落，再按需扩展。

这一层的结果才允许进入证据账本和最终引用。

它回答的是：“文章原文具体说了什么”。

### 7.4 主张层：提炼可比较信息

只有在用户要求逐条拆解或多文章复合分析时，才调用 `article.claims` 或提炼子任务，把原文转换为最小主张：

```text
author / article_id / quote / claim_type / horizon / line_range
```

主张仍然代表作者观点，不自动升级为事实。

### 7.5 外部核验层：确认事实边界

当问题要求“是否属实”“依据是什么”或文章包含关键事实时，主 Agent 再调用 `source.discover` 找线索，并使用 `source.fetch` 读取允许域名的一手来源。聚合新闻只用于发现，不直接作为证据。

## 8. 多文章复合分析

当用户询问“最近一段时间多位作者对黄金的观点有什么变化”时，不能把几十篇文章全文直接拼进一个 Prompt。推荐使用分层 Map-Reduce：

```text
用户问题
  -> Wiki 确定主题、作者和时间范围
  -> 文章目录检索：得到候选文章集合
  -> 去重、按日期和作者分组、控制候选数量
  -> 每篇文章独立读取和提炼主张
  -> 按主题/时间/作者聚合局部证据包
  -> 主 Agent 比较共识、分歧和变化
  -> skeptic / verifier 检查跳步、矛盾和证据缺口
  -> 最终模型自由组织回答
```

这里不同技术的职责是：

- **RAG / FTS5**：缩小候选范围，解决“从大量文章中找哪些”；
- **AgentLoop**：根据问题决定继续读取、扩大范围、核验或结束；
- **Subagent**：在主 Agent 已提供的证据包上做独立比较、质疑或复核；
- **Context 管理**：只保留当前分析所需的证据包、摘要和引用，不保留所有原文全文；
- **Trace**：记录候选数量、实际读取文章、压缩结果、主张数量和最终引用。

### 复合分析的上下文预算

上下文压力不应靠简单截断解决。每层都应该有可解释的预算：

1. 候选文章数预算：避免无关文章进入下一层；
2. 每篇读取行数预算：优先相关段落；
3. 每篇主张数预算：只保留可比较的核心主张；
4. 聚合证据包预算：保留来源、原话和时间，不保留重复叙述；
5. 最终模型预算：只接收与用户问题直接相关的证据包。

如果候选太多，系统应记录“由于预算只读取了哪些文章”，而不是假装完成了全量研究。
