# H2 证据交接与重要结论定向验证草案

日期：2026-10-20。状态：待讨论，未冻结，未实现；不覆盖已确认契约。

后续范围说明：本轮用户授权常规技术借鉴与 MVP 修复，2.1 的锚点补正已单独细化为
[073](073-h2-framework-informed-anchor-repair.md)，仅该窄分支按 073 推进；其余组件仍是草案。

问题依据：[当前归因](../acceptance/harness-v2-root-cause-review-20261020.md)。
本草案细化终稿结构修复、主/子结果交接和验证衔接，不重新选择 A-E，也不调整预算、模型或数据库。

## 1. 目标

让主 Agent 能正确使用委派结果，发现并修订对答案重要的推理、归因与条件错误；
让两层委派的来源链既可追溯又能通过父任务已有权限使用。

沿用当前产品决定：Agent 决定读什么、哪些判断重要、是否委派与是否联网。
不能因为验证不充分而丢失完整分析；作者原观点、反向证据和模型判断并列保留。
主 Agent 不必重新读完所有子任务原文，也不必亲自重做全部分析。

## 2. 拟采用的交接流程

```text
子任务读取授权资料并分析
  -> 保存自由分析、实际依据、限制与可回查引用
  -> 结构补正区分分支；可解析终稿冻结正文，只修指定元数据
  -> Runtime 检查结构/权限/版本/摘录，保存来源链
  -> 父任务取得可用结果句柄与来源身份
  -> 主 Agent 按任务读取所需分析，选择重要结论并判断采用/补查/复核
  -> 自行或委派定向验证，必要时修订解释
  -> 按当前答案版本记录检查结果与未完成项
  -> 交付完整答案，明确范围、争议和未验证部分
```

不是要求每题创建 analyst、verifier、skeptic 三个固定角色。简单查值可能只需来源校验；
解释作者思路时重点核对归因和条件；重要外部事实才按问题决定是否取外部证据。

以下五个组件分别有明确输入、输出和验收，避免把所有问题统称为“加强 Prompt”。

## 2.1 优先组件：终稿正文不随结构补正重写

RC12 证明：原始 5,613 字符正文在一次锚点补正后变成 2,073 字符，并新增虚假矛盾、
跨篇前提错归和排他性方法判断。仅让同一模型重新输出完整 JSON，不能保证只改结构。

建议将补正拆成两个分支，保持同模型、原预算、原截止时间和当前补正/重发次数：

| 分支 | 处理 |
| --- | --- |
| 响应不可解析，或正文必要字段本身无效 | 仍按 065 隔离拒绝输出并有界重建；无法证明保留了原分析，不标记为正文无变化 |
| 完整 JSON 已解析，正文及候选字段有效，仅分析锚点/绑定元数据失败 | 先保存原正文及 hash；补正只返回受限的元数据 patch，Runtime 复用原正文并验证 patch，禁止改 content/candidate_answer |

“冻结”只表示修复不能改正文，不表示正文语义已验证。后续 Agent 正常语义修订仍可产生
新版本并说明理由；不能借一次格式补正静默进行新研究或语义改写。
Runtime 对新增、删除、替换的绑定留审计；非法 patch 不接纳，已有可保留分析仍交付并披露限制。

这个分支有两种需要明确选择的做法：

1. 推荐：允许模型只读已解析候选中的分析字段作锚点定位，再提交限定的绑定 patch。
   Runtime 提供带候选 ID、hash、字段身份的只读视图；分析明确为待验证内容，不能变成
   工具观测、授权或已核实来源。原始工具/来源仍来自可信执行上下文；补正阶段不执行
   新研究工具。输出只能改指定元数据，且必须对原正文重新验证。这是对 065 不回喂
   拒绝分析的窄化例外，需要用户确认，不能沿用原批准自动开放。
2. 严格维持 065：不给模型任何拒绝分析，只剔除可机械识别的无效绑定，保留原正文和
   合法绑定，以 partial/incomplete_metadata 披露缺口。不能猜新锚点、重写分析或认证
   无依据结论；本例全部 28 项都失配，证据覆盖会显著不足。

推荐第一种以恢复有用的原文证据绑定，但它仍有把候选错误误当事实的风险，需专门验证
信任边界；不宣称用标签就消除了注入风险。若不确认此例外，保持现有运行逻辑，先讨论。

验收必须同时满足：正常补正后正文与 candidate_answer 的 hash 不变；锚点严格对应
原正文；原文摘录对应真实来源；伪造工具结果/来源不能进入实际观测；不得执行研究动作；
不新增语义改写；补正失败保留完整分析；全部物理请求、未知与重发仍计账。
不能只检查新 JSON 合法或模型声明“我没有改正文”。

## 3. 组件一：区分可用句柄与来源身份

### 当前缺陷与建议

RC07 的问题是主/子上下文把“知道某个来源存在”与“当前可读取并用作绑定”混在一起。
建议保留原有结果、来源表和权限，不新增一套授予原文权限的机制。

| 概念字段，名称待契约确认 | 语义 | 不代表什么 |
| --- | --- | --- |
| `usable_evidence_handles` | 当前调用方获准使用的结果/材料句柄；注明读取方式、绑定对象及是否已读到所需范围 | 不代表语义已验证，也不代表所有句柄都已读 |
| `source_lineage` | 原文章作者、日期、版本、范围及原读取 Task；沿用 062 的 Runtime 事实 | 不代表父任务拥有原 Artifact 权限或亲自读过 |
| `result_validation` | 结构、来源和摘录的校验结果 | 不代表作者判断或模型推理正确 |

父任务可引用自己有权读取的子结果；原文 ID 留在来源链用于回查。
不能把孙任务私有 Artifact 平铺成建议父任务使用的 evidence_ref。
新视图中的“可用”由实际权限和支持的读取方式决定，不由模型自报。

### 精确的证据绑定边界

引用子分析是间接依赖，引用原文是直接依赖，不能把两者伪装成同一种读取事实。
父任务引用子分析中的一段时，以父任务可访问的结果句柄和该段分析文本绑定；
Runtime 保留该段已有的原始来源链。不能静默把错误的原始 Artifact ID 改成另一个 ID。

如果父任务要声称逐字引自原文，而引用文字只位于子结果的 quotes 字段、不在其分析正文中，
必须有明确的原文摘录访问与绑定契约。当前 `_source_text` 只返回分析正文/候选正文，
不能默认把整个 JSON 任何字段都当成可核验原文。建议本轮先明确拒绝错误绑定并提供
可访问子结果及正确绑定方式；按需证据片段 section 的正式格式另行确认后实现。

不默认复制全部原文，不自动扩权，不把 partial 结果升级为完整来源。
旧结果没有新字段时保留可读性，无法确认的句柄不得伪造为可用。

### 验收

用真实 SQLite/FakeRedis 和模拟模型执行深度 0/1/2：只有孙任务读原文，子任务与 Root
使用各自可用的返回句柄；两次来源链都能传递，原读取 Task 不变，原私有 Artifact
仍拒绝父任务直接读取。另验证 partial、未读尾页、换版本、跨 Run 与未授权 section。

## 4. 组件二：重要推断随依据一起交回

不要求每篇文章填满 ArticleCard，不把整篇文章拆成原子句子，也不统一分析章节。
继续以连贯理解为主；对影响答案的重要跨篇归因、矛盾判断或强因果推断，交接应能说明：

- 这是什么判断：作者原意、跨篇综合还是分析者推断。
- 依据来自哪些文章，以及各篇在判断中的作用；作者、日期和条件分别是什么。
- 目前支持到什么程度，有何反例、限制或尚未核对的部分。

优先利用现有 evidence_links、limitations、gaps 和可选 evidence_additions 的语义；
暂不批准新增全量逐主张 Schema。某个判断没有来源，不等于必须删除，可作为清楚标记的
假设或未验证解释交回，不能通过空引用冒充已支持结论。

Runtime 只检查字段、引用、版本、逐字关系和实际观测，不能自动判定“观点互相矛盾”。
Agent 保留自主推理，但解释强度应和证据范围一致。

验收用 RC01-03 的真实错误及对应合理表述作对照：既纠正错误，也保留正确的综合和批评，
不能通过一律写“无法判断”或删去分析来取得表面通过。

## 5. 组件三：主 Agent 定向验证与状态记录

### 先分清已有要求与待确认细节

[architecture](../architecture.md) 已要求实质分析后验证，方法由主 Agent 自主决定。
[026](026-finance-state-update-protocol.md) 允许不提交状态增量并带 incomplete_metadata 交付。
两者应分别表达行为期望与记录完整性；不能把缺字段直接判成金融事实错误。

H2 需要补齐简短的阶段提醒和按需验证说明入口。建议复用现有 evidence_review 的业务原则，
先核对 H2 可用工具和输入输出再适配，不能把包含旧工具的整个 Skill 无条件塞入新上下文。
本草案不直接批准重启旧版逐句审核或恢复全部 Skill 初始注入。

### 模型负责的判断

主 Agent 在综合时选择影响答案的重要结论，自行检查或委派：

1. 作者观点：原文是否支持该归因，语气、时间、对象、条件是否被加强或混淆。
2. 跨篇关系：比较项是否可比；必要条件不确定是否被误称为矛盾；不同日期是否只是修正。
3. 自身推断：推断所需的前提来自哪里，结论是否超出这些前提的支持范围。
4. 外部事实：问题是否确实需要独立验证；需要时才选择工具取证，否则说明未独立核验。

主 Agent 接受子结果不等于复制全部结论，也不等于对每句默认不信任。
已有核验可以在判断及其证据未变化时复用；候选被实质改写后，旧核验不能自动覆盖新结论。
对弱证据结论仍输出有用分析与局限，对发现错误的解释修订并保留作者原意。

### Runtime 负责的记录

建议先以现有 review/coverage 状态快照表达检查目标、依据、结果与未完成原因，
再为快照绑定候选版本或检查对象指纹，避免上一版检查被当作下一版已完成。
具体版本字段、大小边界和事件名在下一步接口细化时确认，此处不宣称已实现。

运行记录分别显示：

| 维度 | 表达什么 |
| --- | --- |
| 调度/交付 | 是否完成任务并保存、交付正文 |
| 来源/读取 | 实际读了什么、读到哪里、最终依赖什么 |
| 验证执行 | 可观察的检查是否记录完整、部分或未记录 |
| 判断结果 | 支持、反驳、不确定等，不与执行成功混合 |
| 记录完整性 | 可选状态是否完整，不是金融事实可信度 |

模型填 complete 只证明提交了这样的判断，不能充当独立复核或客观正确性证明。
缺少记录、工具失败或意见分歧时保留全文，准确披露，不阻断可交付分析。

### 验收

Trace 能定位检查对象、候选版本、所用材料和执行者；简单任务不被迫派出 reviewer；
不需要联网的作者归因核对不产生无意义外查。无记录不得声称已经验证，审核异常仍
保留完整分析。人工复查判断本身是否正确，不将“存在 review 对象”当成内容通过。

## 6. 组件四：分层验证改进是否有效

不以单次结果更长或多调用一个 Agent 证明方案优秀。建议冻结：

- 同一语料、模型 profile、问题、预算与工具版本；保留旧结果，不覆盖历史批次。
- 离线接口用例先验证权限、版本、部分结果、两层来源链、检查记录和交付保留。
- 内容回归包含必要条件/矛盾、跨日期归因、样本概括、真实反例四组正反例。
- 真实运行仍覆盖单篇推理、作者概括、多作者比较及深度二委派；诊断题和自然 Query
  分开，不能把被指定的成功调度推广成 Agent 会自主选对路径。
- 暂不新增自动评分。人工记录：重要归因错误数、条件/范围错误数、虚假矛盾数、
  正确分析保留情况、完整交付、总请求数、补正/重发数与耗时。
- 新方案至少对选定真实任务各重复三次作为初步对照，先看逐次结果；这不是生产成功率
  证明。若做严格 A/B，则新旧方案按同一冻结条件运行并分别记账，不能直接拼历史批次。

既有错误消失但有用分析也消失不算改善；状态完整但逻辑仍错也不算改善。
真实 Redis、负载与生产入口属于独立验收，不混作此次语义方案的效果指标。

## 7. 待细化和实施边界

建议下一步先确定 2.1 的终稿补正边界，再确定组件一的可用句柄视图及组件三的定向验证记录，写正式接口，
最后进入实现和对应测试。用户已有决定继续有效，不重复询问是否保留全文、是否由主
Agent 自主判断、是否允许自动换模型等已明确的问题。

尚需细化：句柄能支持何种绑定、原文摘录的按需访问、候选版本与检查记录的关联、
无记录时对用户的披露位置，以及是否需要补一次记录的有界机会。
不能把调度信封元数据补交自动等同金融语义重审，也不能让补记录重新生成研究稿。

RC04 的分析锚点重复文本负担按 2.1 处理恢复，首发生成结构暂不更换；RC05 的首发协议
合规率继续观察。当前不增加补正次数或更换模型。RC08 收尾转换另立设计，不扩大本轮。

批准前不修改运行代码，不新增门控、不调整现有重试/预算、不迁移数据库、不切默认 1.0。
