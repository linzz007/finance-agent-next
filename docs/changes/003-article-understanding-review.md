## 1. 本轮要回答的问题

根据[产品目标](../product.md)，先检查文章读完后留下什么，主 Agent 如何利用这些信息解释作者的思路、比较观点并形成有收获的回答。用户认可的“培风客最近三个月观点总结”是回答质量参照，没有其执行 Trace，不能据此推定它使用了某种内部方法。

保留 A1、B3、C1、D*、E* 既有选择；本轮不是重新选择论文，也不是批准每篇文章必须生成卡片或启动 Subagent。

## 2. 已确认设计与当前实现

现行规则见[架构第 4、5、8 节](../architecture.md#4-单篇文章与文章集合)和[接口契约](../finance_agent_interface_contracts.md)。当前存在三条可选阅读路径，不能把其中一条当成全部系统的必经流程。

| 路径 | 当前输入与执行 | 留给主 Agent 的主要内容 |
| --- | --- | --- |
| 主 Agent 直接阅读 | `article.read` 获取单篇文章的指定范围，主 Agent 自己继续分析、回读或保存笔记 | 工具观测中的原文及 EvidenceRef；不会自动生成 ArticleCard |
| 单篇模型处理工具 | `article.study(article_id, question, depth, ...)`；skim 分析指定段落，deep 顺序处理每段最多 100 行的全文，再尝试文章级归并 | 带原文引句、条件、期限和证据的 claims、card ID；deep 还可返回关联的 research_note 及限制 |
| Analyst Subagent | 主 Agent 委派任务，Runtime 绑定文章范围、工具与预算；子 Agent 可调用授权只读工具 | 结构化 claims、证据引用及运行状态；Runtime 将子任务实际读取的证据并入父 EvidenceLedger |

`article.study` 是由固定代码组织模型调用的工具，不是可自主选工具的完整 Subagent。其输入中只有当前 `question` 等任务字段，并不会自动收到父 Agent 的全部对话、计划或其他文章。

当前两种综合路径也应分开理解：

- 主 Agent 可以利用自己可见的正文、工具结果、研究笔记和子任务结果直接综合，最终答案仍由它组织。
- 可选的 `research.synthesize(question, card_ids)` 只接收 2-20 张卡片，把 claims、引句、条件和日期送入综合模型；超过 24 条主张时先选取工作集，提出关系后再用本次完整卡片集审核。它不直接接收原文全文、文章级 research_note 或 AnalystOutput。

这里的“完整卡片集”只代表传入的这些卡片，不代表完整语料或已经覆盖全部正文。关系审核可以发现卡片中被选取步骤遗漏的反例，不能找回最初根本没进入卡片的观点。

上下文压力下，旧工具观测可换出为可恢复 ID；原文和证据不因此被改写。保存成功不代表它仍在模型当前可见上下文中，也不代表模型会正确判断何时恢复。

## 3. 本轮发现与归类

### F1：深读归并的文档表述不一致

- 设计要求：深读不仅取得全文，还要进行文章级归并；归并不成功须能区别于完成深读理解。
- 运行 Skill 的现有表述：`research_artifacts.md` 第 5 行仍称 article-level merge 为 optional。
- 实现现状：deep 会调用归并；异常时保留卡片，在 limitations 写入归并错误，仍返回 `status=studied` 和空笔记 ID。归并模型返回空 entries 时同样没有笔记，但没有单独结果字段区分这一情况。
- 归类：Skill 与现行规范的表述冲突是已确认设计内的对齐项；状态粒度需在接口复核时明确，不能仅凭 `studied` 宣称文章级理解成功。保留有用卡片和分析的原则不变，不应为了状态对齐而删除结果。

定位：[架构](../architecture.md)、[运行 Skill](../../plugins/skills/finance/research_artifacts.md)、[单篇处理实现](../../src/policy_impact/domains/finance/article_study.py)。

### R1：先提取、后归并有信息遗漏风险

- 实现事实：deep 以每段最多 100 行顺序提取 claims；后续归并模型接收 claims 及引句，不接收完整原文，也没有工具回读能力。
- 可能影响：分段抽取没有保留的铺垫、限定、主线或论证联系，归并调用自身无法补回。主 Agent 仍能另外回读，不能说整个系统无法恢复。
- 归类：现行契约明确了分段方式，这不是未遵守契约的证明，也没有真实测评证明它已经造成某次错误；是否调整阅读与返回机制属于设计判断。

定位：[ArticleStudy.call 与 _merge_article](../../src/policy_impact/domains/finance/article_study.py)。

### R2：单篇整体理解与跨篇工具输入并未直接衔接

- 实现事实：文章级归并可保存 research_note 并返回主 Agent；`research.synthesize` 重新从卡片构造输入，不加载该笔记。
- 可能影响：主 Agent 直接综合和调用综合工具时能看到的信息不一致；文章级归并形成的关系不会自动进入后者。
- 归类：当前接口本来限定为卡片输入，因此不是接口违约；是否让综合能力接收整体文章理解，以及如何保留证据链，需要共同决定。

定位：[文章归并输出](../../src/policy_impact/domains/finance/article_study.py)、[综合输入构造](../../src/policy_impact/domains/finance/research_synthesis.py)。

### R3：不同阅读路径的公开分析表达能力不同

- ArticleCard 有 kind、statement、quote、conditions、horizon 等字段；research_note 可以保存较连贯的证据绑定陈述。
- AnalystOutput 当前只有 claims；每条 ClaimItem 包含 claim_ref、statement、evidence_refs 和置信说明，没有单独的文章整体理解、条件、期限或局限字段。
- 子任务仍可在 statement 内表达这些内容，来源元数据也可通过 EvidenceRef 解析；字段不存在不等于信息一定丢失。但不能声称各路径已经提供相同的信息保留与校验能力。
- 归类：是否采用共同的任务导向文章理解表达，需要接口设计；不应未经确认强迫所有路径填同一份长表。

定位：[子任务输出模型](../../src/policy_impact/runtime/subagent_outputs.py)、[研究产物](../../src/policy_impact/domains/finance/research_artifacts.py)。

### F2：委派路径仍有需要单独核对的业务特例

当前金融 Runtime 限制最多 5 个委派，analyst 每批最多 3 篇；满足多作者及篇数条件时，还会预留一个委派名额用于 skeptic/verifier。前两者可作为工程预算候选，但其适配范围尚未在本轮确认；最后一项直接依据业务条件限制研究选择，需要与“主 Agent 自主委派”的现行设计单独核对。

这不表示最多只能读 15 篇文章：主 Agent 仍能直接读取，单篇处理工具也不是这类 Subagent 委派。不能把委派次数当成阅读覆盖的上限或质量证明。

归类：可见代码事实，具体设计依据与修正方案留到委派/预算复核，不在本轮顺手删除安全与资源边界。

定位：[金融 Runtime 的 delegate 实现](../../src/policy_impact/harness/agent_runtime.py)。

## 5. 后续如何证明改进

此处保留证明方向；已确认语义的检查要点见[验收补充第 6 节](../finance_agent_eval_v1_acceptance.md#6-文章理解交接与全文优先的增量检查)。不修改现有 1.0 Query，不引入自动评分或数值通过阈值：

1. 对同一文章、同一问题和同一模型配置，检查任务相关观点、重要条件、论证关系、时间与证据是否保留，记录遗漏而不只检查 JSON 合法。
2. 对多篇综合，追溯重要概括由哪些文章理解和正文支撑；检查例外、反向观点和时间修正是否被抹平。
3. 结合用户认可的回答参照，分别审查研究可靠性和解释价值；不要求复制其七点结构或具体结论。
4. Trace 分别展示实际阅读范围、模型处理输入输出、子任务范围、产物引用、必要回读与交付；不要求暴露模型隐藏思考。

本轮结论仅基于设计与代码静态阅读，未证明现有模型的真实遗漏率、最终答案质量或某个候选优于其他方案。

## 6. 已确认的输入、结果与衔接

用户在确认第 4 节后，又对交接方案与全文优先读法回复“同意”。本节的任务输入、自由理解与来源外层及综合职责由此获确认，不等于已经批准一个 JSON Schema 或新增工具定义。继续复用既有权限、EvidenceRef 和运行标识；不为本轮产品目标引入新的数据库或调度框架。

### 6.1 主 Agent 交付什么任务

主 Agent 指定用户原问题、本次单篇任务、目标文章和预期阅读范围；按需补充关注点、用户要求或有来源的背景，不默认复制整段父对话和所有文章。Runtime 绑定授权、来源版本和实际可用工具，而不是根据关键词替主 Agent 改写分析目标。

同一篇文章可因任务不同而保留不同内容。例如，“概括作者的核心观点”侧重文章主线及其条件；“解释这个结论有没有漏洞”侧重该结论的依据、假设、论证联系与未获支持之处。这些是任务差异的说明，不是要在代码中分类后选择固定路径。

### 6.2 返回内容分为自由理解与可核对外层

| 部分 | 已确认的职责与自由度 |
| --- | --- |
| 连贯文章理解 | 模型围绕当前任务组织文字，不规定必须填满观点、事实、预测等所有栏目；必要时说明作者的论证联系，并区分自己的解释 |
| 来源与阅读范围 | Runtime 记录文章身份、作者、发布日期、版本与实际观测范围；完整读取与模型处理是否完成分开记录，不让模型用一句“已深读”替代证据 |
| 证据联系 | 对影响理解的重要说法保留原文定位或 EvidenceRef；不要求每句话都转成 claim，不把能找到引句等同于推论已经获证 |
| 局限与处理结果 | 保留未读范围、没有相关内容、含糊之处或处理失败；全文取得成功不等于分析成功，有用的部分结果仍可返回 |
| 可选细粒度产物 | 按核验或比较需要附带结构化主张或关联既有卡片，不要求为了调用后续能力再把全部理解改写成 claims |

这里的“分析”是面向用户任务、可以检查依据的解释，不是要求输出模型私有思考。后续第 10 节已选择新增版本化研究结果及来源外层，不把连贯理解硬塞进现有 research_note 或 claims-only AnalystOutput；具体定义见接口契约第 8 节，不承诺当前结构已经能够承载。

### 6.3 主 Agent 如何使用结果

职责关系是：主 Agent 派发或自行确定单篇任务，取得带来源的文章理解后，判断它与问题的关系；按需回读、继续取材、比较或形成答案。没有明确关系时可以不纳入终稿，不以生成了产物作为必须引用的理由。

跨篇综合应能利用这些连贯理解以及其来源、日期和条件，而不只看到被拆开的观点列表。综合发现关键条件不清或矛盾时，应能由主 Agent 补读原文或安排进一步任务；不能用对摘要再摘要来假装检查过正文。这是已确认的衔接语义，不是当前 `research.synthesize` 已有的新参数。

分析较多文章时，应让原始证据、完整文章理解和用于当前综合的工作视图分别可追溯。主 Agent 或获授权的综合执行者按需展开具体内容；工作视图不能变成唯一存本，也不能因上下文换出而丢失来源。复用现有 E* 恢复原则，加载方向及职责已在第 9 节确认，运行内保存与读取映射见第 10 节及接口契约第 8 节；具体容量数值与可执行恢复代码仍待实测和实现。

分析后的验证仍由主 Agent 选择重要对象：既检查是否忠实表达文章，也按问题检查重要事实、因果或自身推断。它不等于每篇文章都先联网，或者每个观点都被 Runtime 拆开审核。验证局限应保留在综合与交付中。

## 7. 已确认的全文优先读法

用户已在后续确认中选择全文适配时优先提供全文；此前“选择主要返回形式不自动批准读法”的未决项已获得明确裁决：

| 候选 | 机制与取舍 |
| --- | --- |
| 全文适配时优先提供全文（已选择） | 对能容纳在本次模型调用可用输入预算内的短文，让分析模型看到全文并形成任务导向的整体理解；超过预算再分段并进行文章级整合。保留论证上下文，但仍需检查遗漏，全文可见本身不是理解质量证明 |
| 保留固定分段提取后归并（不作为默认读法） | 继续先按最多 100 行提取，再由归并模型组织连贯理解；工程边界可预测，但跨段上下文与首轮提取遗漏的风险继续存在 |

不以行数或某个未经实测的“舒适窗口”直接判断全文是否可用；还需为任务指令、工具定义、模型输出和后续处理留资源。具体数值、超长文章分段与回读实现、重试次数尚待设计。分段路径需要文章级整合；一次全文分析已经形成整体理解时，不额外强制一次归并调用。此处的全文优先仅指已选择深读或整体理解能力的调用，不要求所有文章都深读，不改变主 Agent 自己读、浅读或委派的自主权。

本项已确认，其语义已同步架构、接口目标和验收。后续第 8 节的执行载体及第 10 节的版本/兼容映射也已获选择；字段已正式定义，预算策略仍待实现前复核。在用户批准实现迭代前，仍不改运行代码或 Prompt。旧 Skill 与代码的不一致保留为待对齐项，不能通过只改文档宣称修复。

## 8. 已确认的执行载体

用户于 2026-10-16 回复“选择第二种”，确认具有只读工具循环的可选阅读 Subagent。相同的文章理解契约原本可由固定调用工具或受控子任务执行；此次确认选定后者，不直接注册实际的新角色名或工具名。

| 候选 | 如何执行 | 取舍 |
| --- | --- | --- |
| 单次分析为主的工具（未选为新阅读能力的主要载体） | 代码准备任务和全文，调用模型返回文章理解；需要补读时把缺口交给主 Agent 决定 | 执行路径较简单，但该次分析调用不能自行查阅其他授权原文段落；主 Agent 承担补读协调 |
