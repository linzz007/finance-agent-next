# 111 核验放行与显式派发约束

日期：2026-10-28。状态：用户已确认，按本文实现并复验；实际结果另记。

## 设计

新 Run 使用规则 v5；已有 v1-v4 Run 从自身冻结资产恢复，继续原合同，不改写历史结果。
通用 Sub Agent 的轻量输入和普通验证任务保持原工作方式。本文只扩展 Analyst 专业核验。

1. Analyst 2.0 派发必须明确 required、auto 或 off。缺失返回字段诊断，不再静默采用 auto；
   旧 Analyst 1.0 兼容路径不具备文章核验闭环，不受该字段门控。
   原紧凑字段位置保持 `profile_options.review_mode`；高级 review_options 仍可选。轮数省略时 Runtime 使用五轮；
   只有用户明确要求较小上限时，Root 才设置低于五轮的 max_rounds。
2. 创建 Run 可提供可信结构化 `dispatch_constraints.analyst_review_mode`，冻结在 Root Brief，
   所有深度的派发均校验；冲突或遗漏拒绝创建子任务。未提供时由主 Agent 逐次明确模式。
   自然语言由模型理解并翻译；Runtime 不用关键词猜测用户意图。API/工作台可显式选择该约束，
   调度测试目录把已有题目要求另存为结构化约束，不修改问题内容。
3. 文章核验采用 `finance.review_report.v2`：保留原字段，新增必填 verdict
   （passed、revision_required、inconclusive）、verdict_reason 和 blocking_finding_ids。
   material 且 assessment 非 supported 的 finding 必须是阻塞项。passed 要求没有阻塞项、
   没有本次范围内未完成检查；无阻塞但证据不足应为 inconclusive。minor 建议可随通过报告保留。
4. Runtime 校验准确草稿版本、完整目标与 scope、授权及逐字引用，然后才接受 verdict。
   报告合法与分析通过分别记录。分析者拒绝意见的理由不能代替检验者放行。
5. required 成功出口需要：最终整个 ResearchResult 与 review_targets 的规范化内容哈希，
   匹配同一核验范围下至少一份有效 `passed` 报告，累计 finding 的处置完整且没有 unresolved。
   Run 最多保留五条通过记录，记录含草稿哈希、原始不可变 draft_ref/revision、核验范围与报告引用。
   草稿经过其他版本后又恢复成完全相同的内容时，可复用原报告，但交付仍展示原报告绑定的版本，
   不把新 draft_ref/revision 伪装成曾被检查。相同哈希和范围若后来收到有效的未通过报告，
   Runtime 撤销该哈希的旧通过记录。内容或核验范围不同，必须重新核验；在原预算、时间、深度
   和最多五轮内自动继续，分析者先处理意见并修订。触顶交回 partial 和未完成原因，不能标记
   核验成功。off 不自动核验，auto 可明确跳过；一旦声称核验通过，同样需要检验者判定。
6. 可纠正的领域合同错误（意见编号不符、引用不匹配等）产生具体、有界的失败观察，
   保存候选、下一步重新入队并允许同任务纠正。每 Task 累计最多五次领域补正；
   与动作格式补正、核验轮数分别计数，全部物理调用仍计入原额度。权限、租约及内部错误不降级重试。

执行状态、核验 verdict、最终放行状态及领域补正观察均持久化，可从 Trace 对应的材料/结果检查。
不增加调用预算，不自动切换模型，不把源材料或完整 Prompt 展开到公开 Trace。

## 验证

先验证反例：缺模式不能创建任务；重复派发不可借用前一次选项；Run off 约束不能改成 auto；
检验提出重大问题而分析者拒绝，不能成功；改稿必须复审；通过后原样交付才成功；A→B→A 只在 A 与历史
通过稿哈希及核验范围完全相同时复用 A 的原报告；同一哈希收到新的未通过报告后不能再借用旧通过；
错误引用/编号反馈可纠正且第五次后终止；五轮触顶 partial；跨 Attempt 恢复及旧快照保持原语义。

离线通过后冻结源码、规则、题库和原输入快照，DeepSeek 对 SCH-02/SCH-03 各运行一次。
保留同题主120、各子/孙60、整轮600次/60分钟上限，逐次记账；先完整分析结果再决定是否追加测试。
新记录在 `../runtime-records` 独立目录，工作台测试记录可查看，原失败批次保留。
