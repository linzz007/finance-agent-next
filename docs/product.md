# 金融研究 Agent：产品目标

状态：根据用户既有决定和飞书 revision 181 整理；2026-10-16 用户补充确认本轮使用对象、三项核心需求和认可的回答样例，已记录于下文。其余迁移内容继续共同复核；本文件不批准新功能实现。

## 1. 用户与价值

首先服务当前用户的金融研究：阅读已经收集的微信公众号金融文章，理解作者怎么想、观点怎样随时间改变、不同作者在哪些条件下相似或相反，并按需要结合免费公开资料核查。文章通常不长，但观点密度高；作者、日期、对象和适用条件不能在摘要中丢失。

本轮用于用户个人的日常研究，不需要其他人注册或使用。达到能够真正帮助用户理解金融问题的水平，是本轮产品目标；多用户产品不作为本轮架构改造的前提。

用户要学习作者的思路，也要看到模型的判断依据。因此目标不是输出一份形式完整的报告，而是给出有实质分析、可以回看来源、能够区分观点与事实的答案。不能用调用次数、生成速度、字数或一次成功运行替代质量证明。

用户期望达到其认可的通用 AI 回答水平：紧贴问题，既能解释作者的思考，也允许模型结合自己的知识和判断形成有依据的分析，使用户有所理解和收获。不把答案限制为文章摘抄，也不把模型推断冒充作者原话或已核实事实。

## 2. 已确认的范围

| 范围 | 产品要求 |
| --- | --- |
| 本地资料 | 可以浏览和添加文章，按作者和日期发现文章；Wiki 记录资料地图、个人背景与偏好，不替代文章原文 |
| 阅读 | 每篇文章是独立单位；主 Agent 按问题选择浅读、深读或委派，不要求每篇文章都生成卡片 |
| 综合 | 支持作者画像、同作者时间变化、多作者观点关系；不能为形成共识而抹平少数观点或强行关联不同主题 |
| 外部资料 | 可以搜索文章之外的事实、新闻、概念、行情和官方材料；只使用免费网页和公开接口，不等于模型调用免费 |
| 个人上下文 | 可以结合唯一持仓文件和研究偏好；不杜撰成本、收益、风险承受能力，不隐式修改持仓 |
| 验证与答案 | 先理解任务并规划，分析后进入验证；保留作者观点、反驳理由和未解决争议；审核失败也应尽可能交付安全的完整分析 |
| 插件 | 工具、Skills、Subagent 是主 Agent 可选能力；系统规则把控目标、权限、证据和验证阶段，不穷举每种问题的固定路径 |

不以关键词检索组件或向量 RAG 作为当前文章获取的必经路线。元数据筛选和普通目录导航是辅助能力，主 Agent 决定需要什么材料。

## 3. 业务场景与输出期待

### 3.1 本轮优先解决的三个真实需求

以下顺序来自用户于 2026-10-16 给出的真实需求，不是新增的固定执行链路：

| 优先级 | 用户问题 | 产品期待 |
| --- | --- | --- |
| 1 | 这个博主的这个结论是怎么推理出来的，是否有哪些漏洞 | 解释作者的观点、依据、假设与论证关系，指出推理跳跃、适用条件和证据缺口；不能只复述结论或给一个可信度评分 |
| 2 | 某某博主和某某博主的观点的相同点和相反点都是什么 | 围绕问题比较相似、相反与互补观点，保留作者、时间和前提差异；观点一致不能直接当成事实交叉验证成功 |
| 3 | 帮我总结这个博主的全部的文章，给我讲解一下这个博主的观点都有什么 | 综合解释核心观点、分析框架和时间变化，保留例外与矛盾；明确要求全部时，不能用代表性抽样冒充全部覆盖 |

“全部”应说明实际资料边界，例如当前库中收录的全部文章，而不能暗示已经覆盖作者未收录的文章。若未完成请求范围，应如实披露。全部覆盖不等于每篇都必须采用相同深度或相同分析模板；具体阅读与委派仍由主 Agent 按任务决定。

### 3.2 既有验收覆盖

沿用[业务验收 1.0](finance_agent_eval_v1_acceptance.md)的八类场景及 30 条原始 Query，不另建一份不同测试集：

1. 简单查值：准确给出数值、口径、日期和来源；不强制复杂分析。
2. 单篇深读：解释文章核心判断、依据、条件、论证和空白；用户要求全文深读时不能用摘要冒充。
3. 作者画像：基于代表性多篇正文概括，披露抽样范围，不把一篇文章泛化为长期方法。
4. 单作者时间变化：区分事前预期、事后解释、延续和修正。
5. 多作者对比：在同一问题和可比时间条件下保留相似、相反、互补和无直接观点。
6. 外部交叉验证：分别呈现作者说法、独立资料和模型推断；观点共识不等于事实已证实。
7. Wiki/持仓联合分析：说明与用户背景的关联及传导条件，不臆测未提供的个人事实。
8. 异常与边界：没有文章、来源冲突、联网失败或越权请求时诚实说明，不编造来源，不让已有分析无故消失。

这些是现有验收覆盖，不是问题类型白名单。金融知识解释、临时新闻研究等仍由主 Agent 按问题自主处理；是否补充对应验收题另行确认，不在本轮偷偷扩充 1.0 测试集。

最终正文没有统一必选模板。业务能力应适应问题，而不是让问题适应报告格式。

### 3.3 用户认可的回答质量参照

用户提供并认可了一份“总结培风客最近三个月文章核心观点”的回答。此处只记录其产品特征，不复制文章分析正文，也不将其中的篇数、观点或时间判断登记为已核实事实。

- 紧贴所问的作者和时间范围，说明实际资料的范围及最新文章日期，使用户知道回答讨论的是什么。
- 先形成可理解的总体认识，再按实质主题归纳，而不是逐篇堆砌摘要或展示工具运行过程。
- 不止列出观点标签，还解释观点为什么成立、依赖什么条件，以及不同主题如何联系；同时保留没有答案和条件性推演。
- 对跨时间的材料呈现观点延续与变化，避免把较早判断、后续修正和当前立场混成同一个结论。
- 提供原文回查入口，使用户能够进一步学习和检查；引用存在不等于引用内容已经核实。
- 最后回到问题，形成有信息量的综合认识，使用户对作者的思路有实际收获。

这些是该样例体现的质量参照，不是所有回答的必选章节、固定七点模板或每次都要有时间表。样例正文不能证明其背后逐篇阅读、Subagent、验证或上下文处理的实际过程；本轮没有取得该样例的 Trace，也没有核验其原文依据。

后续验收需要分别观察“回答是否准确、可靠”和“回答是否有解释力、对用户有帮助”。流程合规不能代替内容质量，语言流畅或用户认可也不能单独证明事实正确。具体对照材料与判定办法在验收设计复核时共同确定，本轮不新增自动评分或通过阈值。

### 3.4 后续逐篇阅读要求

用户的最终目标还包括：可以对每篇文章的判断和分析加入自己的要求。系统应保留这种可调整性，但本轮尚未定义这些要求的具体内容、配置入口或接口，不据此实现固定文章模板或新的必经审核步骤。后续结合真实阅读需求确认，再按现有插件与主 Agent 自主决策原则设计。

## 4. 新旧项目边界

新项目为 `finance-agent-next`，原项目的同花顺、企业影响报告和其他个人 Agent 产品保持独立。新项目只带文章、金融 Wiki、持仓及偏好，使用独立数据库，不迁移旧对话和 Trace。

默认 `/report`、HTML 报告工作流和图片内容核查不纳入本轮研究入口。未来如需增加，先单独讨论其价值、权限和验收，不能因为继承代码中存在就默认为新产品功能。

## 5. 质量目标与未确定事项

当前优先准确性、完整性、可追溯性和稳定交付，不以节省 Token 或追求极快回答为首要目标；但无限重试、无限取材也不等于严谨。具体预算、时延与上下文阈值需要设计和实测，不能宣称某个固定值是模型最舒适的设置。

多人使用及大量调用的稳定性保留为后续工程议题，不纳入本轮个人日常研究的交付目标；尚没有已确认的并发量、服务等级、部署环境或租户模型。这些指标需共同定义，再选择队列、事务和数据库方案，不能用本地回归数量证明商业化能力。个人使用仍需稳定完成任务，不能把暂无多人需求解释为不需要稳定性。

本轮已经获得使用对象、优先场景和认可的回答质量参照。接下来共同复核系统架构是否服务于这些目标，以及接口和验收能否证明其实现；没有确认的设计选择继续保留为待讨论，不据此启动技术栈或 Runtime 重构。
