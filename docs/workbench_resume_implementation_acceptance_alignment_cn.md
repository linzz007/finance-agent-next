## 1. 项目到底解决什么问题

项目名称沿用：**AI 技术生态智能研判 Agent Harness**。

面向个人与研发团队的技术资料跟踪与研判场景。用户在 Wiki 中维护自己的背景、关注主题、约束与分析目标；平时直接对话，需要报告时输入 `/report <本轮要求>`。系统结合这些背景获取和筛选外部资料，完成分析、检查与报告生成，并支持对历史结论继续追问。

三个问题与三条简历主线：

| 用户或业务问题 | 对应设计 | 要证明的作用 |
| --- | --- | --- |
| 多阶段处理有依赖，中间数据缺失或格式异常容易影响后续分析 | 受控报告 Workflow | 必经环节按约定执行，失败有明确处理，不把不合格结果当作成功输入 |
| 单次分析可能遗漏条件、推断过度或缺少证据复核 | Subagent 分析与核验 | 质疑与核验意见实际参与最终结论处理，而不只是多生成几段文字 |
| 泛化资讯与用户背景脱节，分析依据和历史结果难查 | 多源资料与 Wiki 关联 | 用户背景影响检索、筛选或排序；结论可以追到资料和当时的背景 |

Workflow、Subagent、Trace 都是解决问题的手段，不是用户需求本身。Skill 是能力封装；Trace 是执行证据，不再单独作为项目的第四个核心卖点。

该项目是具体业务场景中的 Agent 应用工程，不定位为通用 Agent 框架或生产级多租户平台。支持不同画像复用同一套流程，不等于必须实现多租户 SaaS。

## 2. 简历目标表达

以下是已讨论的三条主线。每条中的行为要由当前调用链和测试确认后，才能作为完成态投递；发现缺口时优先补齐或收窄措辞，不以简历倒推虚构成果。

### AI 技术生态智能研判 Agent Harness

**项目背景：**面向个人与研发团队的技术资料跟踪与研判场景，针对外部信息分散、与项目背景脱节、分析结论缺少可追溯依据的问题，构建结合 Wiki 背景资料的对话式研判系统，支持多源资料筛选、影响报告生成与历史结论追问。

- **受控报告 Workflow：**针对资料采集、清洗、结构化与分析存在阶段依赖、中间异常难以定位的问题，将报告生成封装为 `/report` Skill，通过阶段状态管理与输入输出校验组织处理链路，对来源不足、结果缺失等情况记录校验状态与原因，明确报告任务的执行顺序和失败边界。
- **Subagent 分析与核验：**针对单次分析缺少专门质疑与证据复核环节的问题，在主 Agent 中按需委派分析、质疑和核验子任务，通过任务上下文与角色级工具权限限定处理范围，将结构化结果回填主 Agent，为最终回答提供反例、证据缺口及核验意见。
- **多源资料与 Wiki 关联：**针对通用资讯难以结合用户实际背景、分析依据不便查询的问题，将 Wiki 中的项目事实与本轮需求结合，按主题、时间范围及来源质量筛选资料；关联来源快照、分析结果与报告产物，通过运行记录支持资料核查和报告追问。

说明：暂不写“准确率显著提升”“生产级稳定运行”“完整复用原日报 Graph”“自动维护全部 Wiki”或完整 Replay。现有代码、设计目标和实验结果必须分开。

## 3. 目标主链路与职责

```text
用户 Wiki 背景、关注目标、约束、来源偏好
                         + 本轮用户要求
                                 |
                     整理本次任务参数与背景快照
                                 |
                默认对话 / 显式 /report 报告 Skill
                    |                    |
            查资料、回答、按需委派      固定报告 Workflow
                                         |
                       获取 -> 清洗/结构化 -> 去重
                                         |
                       约束过滤 -> 背景匹配 -> 重要性排序
                                         |
                          分析 -> 按需质疑/核验
                                         |
                       结果检查 -> 报告与证据保存
                                         |
                       对话追问 / 新一轮补充分析
```

固定的是报告的阶段依赖、输入输出与失败处理，不是查询主题、日期范围、数据源或结论。用户更改关注目标后，应通过任务参数影响处理，而不是改写 Graph。

职责划分：

| 部分 | 应负责 | 不应负责 |
| --- | --- | --- |
| 对话入口与主 Agent | 理解本轮需求，选能力，必要时追问，汇总最终回答 | 绕过报告校验，凭空宣称流程成功 |
| Skill | 声明报告能力的入口、工具范围、输入与产物契约 | 仅靠文本声明代替运行时权限检查 |
| Workflow | 管理阶段、状态和执行顺序，处理失败与有限重试 | 把每个步骤都交给模型重新规划 |
| Subagent | 完成有边界的分析、质疑或核验任务 | 任意增加权限、修改 Wiki 或直接发布报告 |
| Wiki 与来源层 | 提供背景、关注目标和可追溯资料 | 把用户或网页文本升级成系统指令 |
| Trace 与产物记录 | 记录实际执行、判断依据和结果关联 | 用事后编排的展示步骤冒充真实事件或模型推理 |

## 4. 第一条：受控报告 Workflow

### 4.1 设计理由

一份有用的报告不只是模型生成了一段 Markdown。它依赖有可用来源、数据经过清洗、约束被满足、分析结论能引用证据。前面的结果不合格时，后面不能继续把它当作合格资料使用。

因此复用原 Daily 的设计思想：用 State 保存中间结果，用 Graph 控制阶段，用 Hook 承载生命周期处理，用 Gate 判断当前阶段是否可以继续。它们可以沿用现有实现，不要求为了名词一致新建同名类。

### 4.2 输入、过程和结果

| 位置 | 应具备的行为 |
| --- | --- |
| 任务输入 | 本轮要求、分析对象、时间范围、关注主题、来源约束、报告数量或格式、Wiki 背景引用。使用现有结构扩展，不强制创建全新 Task 类 |
| 获取 | 根据任务选择已接入且允许的来源，记录成功、失败、采集时间、事件发布时间和快照引用 |
| 清洗与结构化 | 统一标题、正文或摘要、链接、来源与时间；不合法内容标记原因，不能只留下“成功” |
| 去重 | 复用现有规则，区分重复转载与新的事件进展；保留可解释的事件标识和原始来源关联 |
| 筛选与排序 | 先过滤日期、主题、来源等硬约束，再结合用户背景排序。重要性分数是排序依据，不默认是概率或已校准风险值 |
| 分析 | 根据候选资料和背景事实生成带证据引用的结论，区分来源事实、用户背景和模型推断 |
| 核验与输出 | 按第5节处理必要的核验，再生成报告；成功、部分覆盖、待确认和失败不能在展示层全部变成成功 |

### 4.3 底层执行逻辑

```text
读取当前阶段需要的 State 子集
-> before hook：校验输入，记录阶段开始
-> 执行当前 handler
-> after hook：检查输出，记录真实结果或异常
-> Gate：通过 / 允许重试 / 停止或返回受限结果
-> 通过后才推进下一阶段
```

必须明确四个细节：

1. **重试边界。** 哪些错误可重试，最大次数是什么；重试时清理或替换哪些阶段输出，避免重复追加产生脏状态。不会自动恢复的错误就如实失败。
2. **副作用边界。** 重试不应重复发布报告或无意重复写入长期资料。优先沿用现有产物保存和调用限制，不因此引入分布式事务。
3. **结果语义。** “没有可用来源”可以产出诊断说明，但它不是已经完成有依据的分析报告。部分主题有证据时允许明确标注范围，不必为了形式完整编造其他主题。
4. **真实记录。** 阶段开始、结束、失败、重试应来自执行位置；若某部分只有结束后的汇总记录，要标记为汇总，不编造起止时间、独立工具调用或思考过程。

### 4.4 对原 insight_engine 的复用要求

设计意图是把原日报能力接入 Workbench，但当前已查看的调用链使用 policy_impact 自己的执行器。后续实现应先对比复用范围：

- 原入口：`insight_engine/src/insight_engine/skill_executors/daily_news_report.py::run_daily_news_report_skill`。
- 原控制：`insight_engine/src/insight_engine/harness/graph.py` 及其 Hook、Gate、State。
- 当前入口：`policy_impact/src/policy_impact/harness/agent_runtime.py::_run_external_impact_report` 与 `_run_external_impact_workflow`。
- 当前新闻执行器：`policy_impact/src/policy_impact/skill_executors/recent_news_report.py`。
- 当前政策执行器：`policy_impact/src/policy_impact/skill_executors/policy_weekly_impact.py`。

优先复用已经有效的阶段控制和业务处理，只做输入、State、来源、产物与运行关联的适配。保留 policy_impact 已有的日期/来源/相关性校验，不能为了“复用旧代码”倒退这些能力。

最终只能有一条明确的目标报告执行链。可以调用原能力，也可以迁入必要模块；最终说明究竟复用了哪些代码、哪些只是设计思路。不要复制一套流程后仍让实际入口走另一套；兼容路线应有明确用途，不顺手删除无关业务。

### 4.5 面试怎么展开

“我先把报告拆成有依赖的处理阶段，再用状态和阶段校验约束推进。模型负责内容分析，程序负责哪些步骤必须执行以及异常如何处理。”

需要拿出一个正常流程和一个失败流程，说明失败发生在哪、为什么不能继续、实际如何返回。仅展示一张包含五个步骤的页面不够。

## 5. 第二条：Subagent 分析与核验

### 5.1 设计理由

目标是让分析有专门的质疑和证据复核，而不是为了增加 Agent 数量。多个角色不自动代表独立判断或更高准确率，是否有收益需要看错误发现与结论处理的证据。

### 5.2 角色与返回结果

| 角色 | 输入与工作 | 返回给主流程的内容 |
| --- | --- | --- |
| analyst | 选中的资料、用户背景和分析目标；形成候选影响判断 | 候选结论、成立条件、对应背景和来源引用 |
| skeptic | 候选结论及必要证据；找反例、遗漏条件与证据缺口 | 具体问题指向哪条结论，为什么有疑问，需要检查什么 |
| verifier | 待核验结论与可访问来源；检查证据是否支持该结论 | 支持 / 不支持 / 证据不足，引用位置及说明 |

尽量复用已有角色和结构化输出，不为凑齐表格另造一套内核。若 Workflow 已有分析阶段，不要求再让 analyst 重复分析一遍。

### 5.3 与 Workflow 的关系

普通对话可由主 Agent 按需委派。报告中的核验阶段也可以调用同一个 SubagentRunner：固定的是“何时检查、结果怎样处理”的流程契约，子任务仍采用受控委派机制。

不是所有简单问题都要启动全部角色。应定义可测试的触发条件，例如用户明确要求核验、关键结论需要采取行动但证据薄弱、候选结论存在冲突。条件与预算应可观察，不把“模型觉得复杂”作为唯一不可检查的解释。

```text
主 Agent 或报告阶段提出待核验任务
-> 校验角色、工具范围、任务作用域与预算
-> 构建必要的任务上下文，不复制整段父会话
-> Subagent 调用允许工具，返回结构化结果
-> 校验输出结构与证据引用
-> 主流程处理结论并记录结果
```

### 5.4 真正必须补齐的闭环

- 每条核验意见能对应到某条候选结论，不能只有一段泛泛而谈的评论。
- 结论被证据支持时可保留；被反证时应修改或撤回；证据不足时应标注待确认或减少结论范围。
- 无法解决的分歧可以如实展示；不能因多数角色同意就自动判真，也不能要求必须凑成一致。
- 子任务超时、格式不合法或越权请求要有明确返回，不能变成“核验通过”。预算耗尽后停止补查，不无限返工。
- 主 Agent 保留最终表达权，但不能悄悄抹掉重要的未解决核验问题。应保留结论处理结果及理由。
- 输出Schema和引用存在性只能检查结构与可追溯性，不能证明语义正确；最终质量仍需样例答案或人工复核。

### 5.5 面试怎么展开

用一条真实案例说明：初始结论是什么，质疑指出什么，核验读了什么，最后保留/修改/撤回了什么。没有此类结果时，只讲已具备受控委派能力，不宣称准确性已经提升。

主要入口沿用 `harness/subagents.py`、`runtime/subagent_manifests.py`、主循环的委派入口与现有工具网关。对子 Agent 的限制应在实际执行入口生效，不能只有 Prompt 禁止说明。

## 6. 第三条：多源资料与 Wiki 关联

### 6.1 设计理由

同一条技术消息对不同人或项目的重要性不同。系统要结合用户实际背景决定查什么、筛掉什么、重点分析什么；用户也应能追问“为什么把这条排在前面、依据是什么”。

### 6.2 Wiki 最少承载什么

| 信息 | 示例 | 使用位置 |
| --- | --- | --- |
| 背景事实 | 使用的技术栈、部署环境、团队资源 | 相关性判断与影响分析 |
| 关注目标 | 跟踪哪些技术问题，希望作出什么决策 | 检索任务、候选筛选与报告重点 |
| 限制条件 | 只考虑自托管方案、暂不迁移框架 | 过滤和建议边界 |
| 来源偏好 | 优先官方发布，社区信息需标注 | 已接入来源的选择与披露 |

优先用明确的 Wiki 模板与现有事实结构，不把“能读取 Markdown”说成“任意自然语言文档都能可靠编译成任务”。背景事实与关注目标是不同类型；模型推断出的信息不能直接当作用户确认事实。

系统硬约束始终有效；在允许范围内，本轮明确要求可以覆盖 Wiki 默认偏好，但仅作用于本轮，不能静默改写长期画像。分析对象等必要条件缺失时先澄清；不是每个可选字段都要追问。

### 6.3 需要打通的数据链

```text
Wiki 编辑保存
-> 解析事实和目标，更新或刷新检索索引
-> 下一轮读取最新内容，保存本轮实际使用的背景引用/快照
-> 与本轮要求合并为任务参数
-> 筛选已接入来源，检索并过滤资料
-> 匹配用户背景，形成排序与分析依据
-> 报告记录引用，后续按报告标识追问
```

这里要验收的不是“Wiki内容出现在Prompt里”，而是它是否对任务产生符合预期的影响。用同一来源快照、两份差异明确的画像，检查候选选择、排序或建议是否有合理区别。画像变化不一定要让所有结果都变化，但应能解释为何变或为何不变。

### 6.4 来源、持久化与追问

- 来源选择限定在实际接入的连接器和权限范围内；暂不支持的来源应披露，不声称已经搜索全网。
- 区分事件发布时间、实际抓取时间和快照时间；过期快照是否可用由任务要求决定，使用时须说明。测试fixture不能冒充实时资料。
- 保存必要的来源引用、实际使用的 Wiki 内容或可还原版本、任务要求、排序/核验结果与报告路径。复用现有SQLite和产物文件，不要求新建版本管理平台。
- 若父运行和内部Workflow使用不同run_id，保留明确的父子关联，不把不同记录拼成一次不存在的执行。
- 用户问旧报告时按那次报告的背景和资料回答；最新Wiki变化应作为新条件说明。要求重新分析时创建新运行，不能无提示覆盖原报告。
- 对外部网页或Wiki中的越权指令按资料处理，不能修改工具权限。可显示必要执行摘要，但不要展示密钥或伪造模型隐藏思考。

当前已查看到的是Company Wiki Markdown事实读取与上下文构建，不能据此宣称接入某个外部LLM Wiki项目，也不能直接认定关注目标已经完整驱动检索与排序。

### 6.5 面试怎么展开

展示同一批技术更新在两份背景下为什么有不同的优先级，再从一条报告结论追到来源、背景事实和核验意见。这里Trace是证明过程的工具，核心仍是背景关联与证据使用。

## 8. 最小验收集

这是待执行的验收要求，不是已运行结果。可先用可控资料和脚本化模型验证确定性分支，再用真实模型与实际来源核对语义效果；两类结果分开记录。脚本化模型验证的是机制，不证明真实模型准确性。

| 编号 | 输入或条件 | 必须观察到什么 | 留下的证据 |
| --- | --- | --- | --- |
| W1 正常报告 | 一份画像、明确的主题和时间范围、可用资料 | `/report`进入真实工作流，完成必经阶段，产物与引用可打开 | 本轮要求、阶段记录、来源、报告 |
| W2 来源不足 | 无可用来源、全部不匹配或严格要求的最新资料不可得 | 明确失败或受限范围，不用fixture/无关资料冒充完整结果 | 数据源状态、校验原因、实际返回 |
| W3 阶段异常 | 模型输出缺字段或阶段返回非法结构 | 仅按规则重试，超限停止或返回受限结果；不重复产出成功报告 | 实际异常、重试次数、后续阶段是否执行 |
| P1 画像差异 | 同一批资料，两份需求不同的画像 | 筛选、排序或分析有可解释的差异；与无画像基线进行有条件的比较 | 固定资料、两份画像、候选与报告对照 |
| P2 Wiki更新 | 修改一个会影响结果的事实或目标 | 保存/索引刷新成功；新运行用新内容，旧报告仍可解释原依据 | 保存结果、新旧输入背景、检索或分析差异 |
| P3 本轮覆盖 | Wiki默认近30天，本轮明确只要近7天 | 当前任务遵守7天，长期Wiki不被静默修改 | 本轮参数、实际选中事件、Wiki前后对照 |
| P4 来源披露 | 一个来源失败，另一个只有旧快照 | 成功/失败与快照时效真实披露，不宣称全量实时覆盖 | 连接器结果、时间字段、报告范围说明 |
| S1 无需委派 | 普通简单问题，无核验要求 | 按规则直接回答，不强制启动所有角色或重型报告 | 模式、委派判断、真实调用数量 |
| S2 核验改结论 | 可控资料中含一个可明确判错或证据不足的候选结论 | 核验指出具体问题，最终结论修改、撤回或标待确认 | 初始结论、核验证据、最终处理 |
| S3 核验未完成 | verifier超时、输出格式异常或与其他角色分歧未解 | 不冒充已核验；预算有界，保留未解决状态 | 子任务状态、处理分支、最终表述 |
| S4 权限边界 | 子Agent请求角色之外的工具；资料中含越权指令 | 在执行入口拒绝，无对应副作用；返回可理解原因 | 拒绝记录、工具未执行证明 |
| A1 报告追问 | 针对历史报告询问某条结论的来源和适用背景 | 找到该次运行的资料与背景，区分历史分析和最新条件 | 报告标识、运行关联、引用与回答 |

不要为了满足测试写只识别测试句子的特殊分支。确认规则之后，换表达或加入未参与修改的样例复核。真实核验质量由证据与人工标准判定，不能只看Schema通过、工具成功或页面有报告。

## 9. 怎么逐项实施与判断完成

1. **先画当前真实调用链。** 对照三条简历，标记“已有且验证”“有代码待验证”“未接通”“与目标不同”。先复用，不凭印象判断只差测试。
2. **先跑W1–W3。** 确定唯一目标报告链，以及阶段控制和失败返回。根据失败结果决定做适配还是局部重构，不默认直接搬完整旧项目。
3. **再跑P1–P4。** 确认Wiki和本轮需求真正进入筛选/分析，来源状态诚实披露。第三条只有在背景关联可演示后才算成立。
4. **再跑S1–S4与A1。** 复用现有Subagent机制，验证它影响结论且越权不生效，报告追问能找到依据。
5. **同步表达与复盘。** 每次修改记问题、代码/配置变化、测试结果和剩余限制；据实修订简历与面试材料，不先写效果再补数据。

这些是依赖顺序，不是每日计划。若已有测试和产物足以证明某项，可以直接复核并跳过重复实现。验收过程发现新问题时只修与三条主线相关的部分。

整体通过要求：三条各有一个可独立解释的成功或纠错案例，关键失败分支不会被误报为成功，真实来源/模型验证与确定性测试分别留证据。学习验收还需要本人能解释代码决策、输入输出和限制；AI把代码跑通不等于本人已掌握。

## 10. 迭代如何变成面试故事

| 阶段 | 可组织的问题主线 | 表述边界 |
| --- | --- | --- |
| 已有Daily阶段 | 从资料到报告有多个依赖步骤，因此构建受控阶段流程 | 根据当时真实实现和测试讲；没有记录的线上故障不要补造 |
| 已有Workbench阶段 | 多命令与资料维护入口混杂，调整为默认对话、/report与Wiki页面 | 可参考现有改造文档；历史自动化通过不等于当前真实模型已跑稳 |
| 接下来的一轮 | 验收发现实际入口、Wiki关联或阶段失败行为与目标不一致 | 以这次实际发现的问题为起点，记录适配和复测结果 |
| 后续核验改进 | 真实案例中存在推断过度或核验意见未被正确处理 | 记录结论前后及核验依据，再决定能否量化收益 |

每轮不必新增一个模块；修改一个关键判断、校验条件或数据传递也可以是有效迭代。有设计动机可以讲设计，有失败证据才讲“发现该问题后优化”，有对照记录才讲量化改善。

未来若要测量，优先选择：硬约束通过情况、来源可追溯情况、人工判定的相关性、错误结论处理情况，以及包含核验开销的完整耗时与模型成本。先定义样本与判定口径；小样本直接报告通过数/总数，不能把演示结果包装成泛化准确率。
