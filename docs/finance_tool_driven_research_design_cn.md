# 金融 Tool-Driven Research Agent 设计

## 1. 设计目标

本系统不把金融文章预先切块、向量化并自动塞入上下文，也不要求用户准确说出某篇文章的标题。

系统的目标是：

> 用户只描述想了解的问题，主 Agent 阅读 Wiki 中的研究规则和资料地图，自主决定搜索什么、读取哪些文章、是否访问公开网页、是否委派 Subagent，以及什么时候可以回答。

这是一套 **Tool-driven Research Agent**，而不是以 RAG 为核心的问答系统。

## 2. 为什么不以 RAG 为主路径

当前文章库规模不大，而且文章具有明显时效性：

- 新文章的价值可能高于旧文章；
- 用户问题通常是开放式的，不一定对应某个固定主题；
- 用户可能只问“最近市场发生了什么”，并不知道文章标题；
- 文章内容会变化，静态向量索引容易产生过期召回；
- 是否需要读取某篇文章，应由 Agent 根据当前问题决定。

因此本项目不把向量召回作为默认入口。文章库可以保留最基本的目录、日期和 Hash 索引，用于安全列举、去重和排序，但它不是自动注入上下文的 RAG 层。

## 3. Wiki 的新定位

Wiki 不是文章全文数据库，而是 Agent 的**研究控制面**。它告诉 Agent：用户是谁、应该关注什么、资料在哪里、如何判断资料质量。

### 3.1 用户背景

由用户维护：

- 研究身份和关注目标；
- 关注资产、市场和主题；
- 持仓或观察列表；
- 研究时间范围和更新偏好；
- 对作者、机构和公开来源的信任偏好。

### 3.2 研究规则

由用户维护：

- 最近文章优先还是历史文章优先；
- 是否必须查官方来源；
- 哪些来源只能作为线索；
- 作者观点、事实、推断和预测如何区分；
- 什么时候需要 Subagent 复核；
- 证据不足时是否允许给出暂定判断。

### 3.3 资料地图

由系统或用户维护：

```text
TT -> D:/金融/文章数据/TT/articles/
培风客 -> D:/金融/文章数据/培风客/articles/
万种心法 -> D:/金融/文章数据/万种心法/articles/
官方宏观来源 -> federalreserve.gov / bls.gov / pbc.gov.cn ...
```

资料地图只提供位置和访问规则，不把文章内容预先放入 Prompt。

## 4. Agent 可以使用的基础工具

### 4.1 本地文章工具

| 工具 | 作用 | Agent 自主决定的内容 |
|---|---|---|
| `article.list_recent` | 列出作者目录中最近更新的文章 | 是否查看哪个作者、多少篇、什么时间范围 |
| `article.read` | 读取指定文章或指定行 | 是否继续读取全文、哪些段落需要展开 |
| `article.metadata` | 查看日期、作者、Hash、来源链接 | 是否排除旧文章或重复版本 |
| `article.claims` | 对已经读取的文章提取主张 | 是否需要逐条拆解 |

这些工具不向模型自动返回文章全文。模型必须主动调用，调用记录进入 Trace。

### 4.2 公开网页工具

| 工具 | 作用 |
|---|---|
| `web.search` | 根据当前问题寻找公开网页线索 |
| `web.open` | 读取指定网页正文 |
| `source.fetch` | 读取允许域名的一手官方来源 |
| `source.metadata` | 获取发布时间、页面标题和抓取时间 |

聚合新闻、搜索标题和 RSS 只提供发现线索，不能直接作为事实证据。

### 4.3 文件工具边界

不开放任意路径的 `read_file` 和 `write_file`。

- 文章读取必须经过 `article.read`，限制在文章根目录内；
- 用户添加文章通过页面/API 写入，不由模型任意改写原文；
- Agent 只能写当前运行的 `artifact`；
- Wiki 修改需要单独的显式确认工具；
- 所有读取和写入都记录路径、Hash、时间和调用者。

这样既支持文章实时读取，也避免 Agent 越权修改持仓、Wiki 或原始文章。

## 5. 新的 AgentLoop

金融工作空间不再先根据关键词决定“文章模式”还是“行情模式”，而是统一进入一个可以自主调用研究工具的 AgentLoop：

```text
用户问题
  -> 读取金融 Wiki 和资料地图
  -> Agent 判断问题的新鲜度、主题和证据要求
  -> 主动调用 article.list_recent / article.read / web.search / source.fetch
  -> 观察工具结果并决定继续、换来源、委派或回答
  -> 必要时调用 Subagent
  -> 证据门控与引用检查
  -> Agent 自由生成最终答案
```

Runtime 仍然负责：

- 工具权限和参数校验；
- 路径和域名安全；
- 单轮最大步数、调用次数和超时；
- 文章是否真的被读取；
- 引用是否来自本轮读取结果；
- Subagent 是否只能使用已授权证据；
- 失败、降级和未核实状态。

Runtime 不负责替模型决定“必须先搜作者还是先搜网页”。

## 6. 时效性设计

每次研究都建立 `ResearchClock`：

```text
query_time
requested_period
article_published_at
source_published_at
retrieved_at
content_hash
```

Agent 根据用户问题自主决定时间范围，但必须能解释：

- 为什么选择这些文章；
- 为什么排除旧文章；
- 哪些来源是历史背景而不是当前事实；
- 页面当前内容和文章当时内容是否可能不同。

文章目录每次进入 AgentLoop 前重新同步。新文件可在下一轮被发现，不需要手工重建数据库。Hash 用于发现文章修改和重复内容。

## 7. 多文章复合分析

用户不需要知道文章标题。例如用户问：

> 最近一个月关于黄金和美股的主要观点有什么变化？

主 Agent 可以自行执行：

```text
1. 读取 Wiki，确认关注资产、时间偏好和研究规则
2. 列出最近一个月各作者文章
3. 按日期、作者、主题选择一批候选
4. 逐篇读取标题相关段落
5. 对必要文章调用 article.claims
6. 形成内部证据包
7. 判断是否需要公开来源核验
8. 将证据包交给 analyst / skeptic / verifier
9. 根据返回结果继续读取或结束
10. 自由生成最终回答
```

这里不把几十篇全文放进单个上下文，而是使用 Agent 主动控制的分批读取和证据包。证据包至少保留：

```text
article_id / author / published_at / quote / line_range
claim_type / source_url / content_hash / verification_status
```

## 8. RAG、Agent 和 Subagent 的边界

### 8.1 RAG 不作为主决策者

本项目可以使用轻量元数据索引，但不使用向量 RAG 自动决定最终证据。索引只帮助 Agent 快速列举和排序文章。

### 8.2 Agent 负责研究路径

主 Agent 自主决定：

- 先看哪些作者；
- 先看最近几天还是最近一个月；
- 是否继续扩大范围；
- 是否需要读取官方来源；
- 是否需要 Subagent；
- 什么时候证据已经足够。

### 8.3 Subagent 负责独立复核

Subagent 不默认自由搜索所有内容，而是接收主 Agent 已经读取的证据包：

- `analyst`：归纳多篇文章的共同点和分歧；
- `skeptic`：寻找相互矛盾、时效性错误和过度推断；
- `verifier`：检查结论是否真的被来源支持。

是否调用、调用几个、每个任务的 Prompt，由主 Agent 在 Loop 中决定；角色可用范围、工具权限和最大预算由 Runtime 固定。

## 9. 最终输出约束

最终回答不采用固定模板。模型可以根据问题输出简答、比较分析或长篇研究文章。

但无论输出什么形式，Runtime 只检查必要事实：

- 不能把搜索标题当作已核实事实；
- 不能引用没有读取的文章；
- 必须区分作者观点和 Agent 推断；
- 证据不足时必须说明不确定性；
- 涉及最新行情或政策时必须记录数据时间。

也就是说：**不限制表达形式，只限制证据诚实性。**

## 10. 实现顺序

1. 将当前文章 API 和网关扩展为 `article.list_recent`、`article.metadata`，保留实时目录同步。
2. 将金融工作空间从关键词触发文章模式改为统一 AgentLoop 工具自治。
3. 增加 `ResearchClock` 和时间新鲜度判断。
4. 增加证据包和 Evidence Ledger，但不强制最终答案格式。
5. 将 Subagent 接入证据包复核，而不是让其重新自由采集文章。
6. 用“最近一个月黄金、美股、利率观点变化”等开放问题验收 Agent 是否会自行找到正确资料。

最终目标是：用户只负责提出问题，Agent 自己寻找和组织资料，Runtime 只在关键边界上保证安全、时效和证据可追溯。
