## 4. 关键失败归因

### 4.1 不是 Runtime 账本或预算问题

20 道实际题的调用绑定、预算守恒、已发送调用计费、授权模型、产物哈希和调用结算均通过。Q16 使用 6 次、Q18 使用 22 次，分别仍有大量剩余额度，失败发生在公共动作解析/校验阶段，不是取材耗尽或 120 次上限触发。

### 4.2 模型协议遵约不稳定

Q16 的原始动作后带协议外 DSML 闭合文本，补正又带安全标签；Q18 的补正答案内容本身有未转义双引号。当前设计要求公共动作是一个完整 JSON，且不执行 DSML/XML。放宽解析、任意截断后缀或继续重试会改变已冻结的信任边界，因此本轮不修改为宽松解析。

### 4.3 真实分析的主要问题是时间、条件和归因

- Q07/Q10/Q14 把概率预测的一次结果与校准能力混同。
- Q11/Q17 没有把不同日期、事件阶段和指标口径对齐，就形成矛盾或共识。
- Q15 把“非核心变量”改写成“完全无作用”，并出现跨作者数字归属错误。
- Q01 模型读取到了正确的 888 篇索引，但回答成 890 篇，且各作者计数和最新日期也有偏差；这是模型汇总错误，不是分页遗漏。两个列表页实际为 500+388 个不重复 ID。
- Q12 证明了“语法补正”不等于“语义信任恢复”：被 Runtime 拒绝的伪观察没有进入可信状态，但模型在补正时仍引用了这些文本。现有设计已经有“被拒响应是诊断数据、不可当作已执行观察”的提示；本批显示模型仍可能违背它，属于待讨论的修复来源/语义边界，不直接加一个全局金融闸门。

### 4.4 委派和状态披露仍不是稳定质量证明

Q07-Q09 产生了 7 个子任务。Q07 两个子任务均耗尽额度，Q08 三个子任务均因 `budget_denied` 失败，Q09 一个子任务成功返回空证据、另一个失败。Root 可以在有合法结果时交付，但“子任务成功”不能替代完整研究；Q08 还显示模型没有在终稿前刷新子任务状态。当前批次没有证明多作者、多子任务综合的稳定成功率。

## 6. 不应在本轮擅自修改的事项

以下属于设计决策，不因本次结果自动改写：

1. 是否允许对格式补正做更强的来源隔离、明确的“无可信证据则只能披露无法分析”交付策略。
2. 是否增加跨文章比较的日期/条件对齐约束，或只保留在主 Agent 研究提示中。
3. 是否让 Root 在交付前强制刷新子任务状态，还是继续由模型自主选择 `agent.status/wait`。
4. 是否增加模型输出的具体围栏/代理层规范化，以及它与当前“严格 JSON、不执行 DSML/XML”的边界如何兼容。

上述新策略不是已确认的实现规则。本轮审查尚未证明这些语义失败由某个确定的 SQLite、Redis 或动作执行契约违例造成；不能据此宣布已排除所有实现缺陷。已知业务工具接入、研究时钟、规划/审核映射仍有缺口，继续保持未验/不完整，不用新的研究规则掩盖。

建议先解决 Q12 的被拒响应来源边界和 Q16/Q18 的协议容错设计，再验证跨文时间/条件对齐；模型计数、概率解释和作者归因单列质量问题，不通过增加固定阅读次数或强制所有子任务来掩盖。
