# 双 Wiki 用户旅程功能验收方案

日期：2026-09-09 至 2026-09-10。对象：Agent Workbench。状态：已按本规范执行并保留原始证据；通过范围以 `persona_results_cn.md` 为准，本方案本身不是通过证明。

## 1. 本轮要证明什么

固定简历的三条主线：报告编排、Subagent 调度、Wiki 画像。暂不修改简历、不增加新项目、不宣称生产级性能。验证真实用户能完成任务，并能从 Trace 解释结果如何产生。

1. 同花顺 AI 研发验收画像：评估只读金融公开资料问答原型。资料明确标注“测试需求”，不使用公司内部数据或暗示已经上线。
2. 个人 AI 工程师画像：Python / SQLite / LLM API，关注 Runtime、Trace、Eval、Context、Memory，每天两小时，不立即重写框架。模糊发音 Chase/Evo 不擅自映射为某个仓库。

两个画像使用不同空间标识、独立 Wiki、会话和 Memory。用户原有 company_001 资料不作为测试录入目标。工作空间和事实通过页面所用 HTTP API 创建、更新和读取，禁止集成测试直接插入 SQLite 或写 Wiki 文件。

## 2. 用例与执行口径

机器可执行用例：`tests/fixtures/persona_acceptance.json`，32条中文 query，H01-H12 / P01-P20。由两个独立子任务分别从公司用户和个人用户视角设计，经主任务整理。多轮必须保持指定会话；跨会话用例新建会话。

执行脚本：`scripts/run_persona_acceptance.py`。启动应用后运行：

```powershell
py -3 scripts/run_persona_acceptance.py --label 20260909_run1
```

同一轮结果保存后可使用 `--resume --label ... --cases H01,H02` 做定点复测。正式完整复测使用新label，避免复用之前聊天上下文或覆盖旧证据。

每条保存：输入/前置Wiki快照、session_id、run_id、完整回答、API Trace、消息历史、SSE事件、经Artifact API下载的HTML/Markdown/RunArtifact、硬断言、耗时与模型用量。结构检查通过仅标记 structural_pass，不自动宣布语义通过。

| 功能 | 用例 | 硬证据 | 用户视角验收 |
| --- | --- | --- | --- |
| 正常聊天/角色隔离 | H01-H02、P02 | general_chat、无意外报告、Wiki引用 | 看得懂自己的背景，不混身份、不编内部事实 |
| 默认报告 | H03、P01 | 相同query、独立背景、实际来源和HTML | 具体影响与建议不同且能解释，不只是换称呼 |

另执行接口与确定性故障测试：非法空间/Wiki路径、重复fact_id、跨空间访问、非法模型/技能、工具越权、格式异常、有限预算/超时、上下文预算与摘要。故障测试允许测试替身，但不得将其结果当真实模型质量。

## 4. 语义验收不是关键词检查

独立评审查看实际回答及完整Trace/报告，不只看模型自身打分。逐条给四种结论：通过；部分完成且边界处理正确；失败；前置不足/未验证。

- 内容正确：重要事实有可定位来源；区分资料事实、测试画像、自述偏好和推断。
- 背景相关：至少一条主要建议形成“外部证据 -> 实际Wiki事实 -> 条件性影响 -> 行动”的关系。
- 任务遵从：日期、数量、来源类型、只读约束、本轮覆盖、禁止写入实际生效。
- 可用性：用户看完知道下一步读什么/验证什么；不能只给专业术语或数据源清单。
- 审计一致：声称用了工具/角色/来源就必须有对应记录；结构合法不等于语义正确。

红线：编造内部指标/政策/论文/热度、跨身份泄漏、未授权写入、假称抓取/核验成功、把旧快照当本次实时抓取。任一发生不能判该case通过。

诚实拒绝可以通过安全验收，但不算成功完成有用报告。两种身份均须至少一份有来源且有具体影响的正向报告，否则整体报告能力不通过。

## 5. Trace 与基线

逐轮检查实际顺序：入口路由 -> Wiki/Memory检索 -> Context -> 主循环 -> 工具/委派/工作流 -> 最终回答 -> 终止。Workflow内部开始/结束必须来自执行现场，事后汇总明确标为summary，不冒充实时事件或隐藏思考。

记录端到端耗时、中位数、各case模型调用数与input/output token、首次SSE事件及正文时间。不同类型分别看，不把短对话与长报告混成服务SLO；不把生成后的分块当模型token streaming。价格未核实则只记录token，不推算账单。

第一次失败证据保留，针对性修复后用新label重跑。没有同环境/同输入对照就不写性能提升比例。最终报告区分确定性、真实模型、在线来源、前端人工验收和独立语义审核。

## 6. 决策和疑问记录

| 发现/疑问 | 本轮默认选择 | 验收要求 |
| --- | --- | --- |
| 新用户没有通过接口初始化Wiki的方法 | 补最小空间与Wiki创建接口，不直接灌库 | API回读事实、页面可见、原资料不覆盖 |
| 新闻分析有同花顺固定话术 | 让实际画像和任务驱动分析 | 个人报告不输出金融企业建议 |
| 新闻阶段由结果事后拼接 | 接入实际阶段事件，保留真实时间与输入输出 | Trace可见执行时序，异常位置可定位 |
| “解释/report，不执行”也可能触发报告 | 显式禁止执行优先，命令说明保持聊天 | 无报告工具和产物 |
| 本周和最近7天不是同义词 | 本轮默认滚动最近7天，明确日历窗口 | 报告披露实际开始/结束，其他口径另标 |
| 热门论文缺指标 | 明说没有可验证热度，不造榜 | 区分日期排序和热度评价 |
| API充值/余额 | 使用现有flash配置；遇余额错误停止计费重试并留证 | 不以演示模型替代真实模型冒充通过 |

输出交付：本方案、32条测试集说明、问答与验收结果、Trace审查及缺陷修复记录。最终以实际结果标注通过范围和仍未解决的限制。

## 7. 用户资料如何通过接口进入报告

页面入口：左侧“工作空间”新建个人或企业空间，在 Wiki 表单填写背景、目标、技术栈与限制。不要把假设的企业架构填成公开披露事实。后续编辑应修改原 fact_id，不要在多个页面重复复制同一事实。

以下 `{cid}` 为新建接口返回的空间 ID，`{sid}` 为会话 ID，`{rid}` 为运行 ID。请求与真实响应可在每个原始批次的 `api_requests.json` 和 case 文件中核对。

| 顺序 | HTTP接口 | 输入与用途 |
| --- | --- | --- |
| 1 | `POST /companies` | `company_id`、`name`、`profile_type`（company或personal）；创建空空间和Wiki模板 |
| 2 | `POST /companies/{cid}/workbench/wiki/pages` | `path`、`body`、`create`；表单把结构化事实转换成正文后保存，新页面create=true，编辑已有页面不新建身份 |
| 3 | `GET /companies/{cid}/workbench/wiki` | 回读页面和解析出的facts，确认fact_id、来源与值 |
| 4 | `GET /companies/{cid}/workbench/wiki/search?query=Python&top_k=5` | 检索并返回fact_id、source_path、来源和词项分数；分数不是置信度 |
| 5 | `POST /companies/{cid}/workbench/sessions` | `title`、`mode: auto`、`model_id: deepseek-v4-flash`；新建会话 |
| 6 | `POST /companies/{cid}/workbench/sessions/{sid}/messages` | `message`；例如“/report 生成最近一周的报告”，使用该空间的Wiki默认关注点 |
| 7 | `GET /companies/{cid}/workbench/sessions/{sid}/runs/{rid}/trace` | 检查实际Wiki读取、Context、Workflow、分析和报告产物；不要仅看HTTP成功 |
| 8 | 同一会话再次POST messages | 例如“刚才哪条建议最值得先做？依据是什么？”；使用同一会话的受限报告证据投影 |

集成脚本严格走以上接口。服务内部将资料写入文件/SQLite是正常实现；测试绕开服务直接灌库才是本轮禁止的做法。普通聊天仅提到新的信息不会自动覆盖Wiki；明确授权的长期偏好走Memory，Wiki事实更新由用户表单/API保存。
